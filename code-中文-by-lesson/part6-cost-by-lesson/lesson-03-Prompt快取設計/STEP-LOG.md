## Step 1：閱讀快取設計指南，理解原理

### 閱讀任務

打開 `docs/cache-design-guide.md`，回答：

1. Prompt 快取快取的是什麼？（對話歷史 / 系統提示 / 兩者都有）

   答：**系統提示（固定部分）**——CLAUDE.md、系統 prompt 等「每次送出都一樣的 context」。對話歷史每一輪都新增一筆，前綴每次都不同，所以**不會被快取**。

2. `claude --continue` 和成本有什麼關係？

   答：`--continue` 從同一個專案目錄接續先前對話，讓 Claude 送出與上次**完全相同的 context prefix**，**最大化快取命中率**。每次新開 session 反而比接續舊 session 更貴，因為快取要重新建立。

3. `DISABLE_PROMPT_CACHING=1` 在什麼情況下有用？

   答：**除錯時**——當懷疑 AI 用了過期的快取 context，臨時關掉確認「AI 看到的是最新 CLAUDE.md」。正常使用不應關掉，關掉等於放棄 90% 折扣。

### 實際結果

讀取 cache-design-guide.md 確認：快取對象是系統提示（CLAUDE.md），不是對話歷史；`--continue` 最大化快取；`DISABLE_PROMPT_CACHING` 除錯用。

## Step 2：理解「Exact Prefix Matching」的致命性

### 概念說明

快取的比對方式是**完全前綴匹配**——從第一個字元開始對比，
只要某一個位置不同，從那個位置之後的所有內容都必須重新計算。

### 情境練習

假設你的 CLAUDE.md 頂部是：

```markdown
# 我的專案（更新於 2026-06-13 15:30）

## 技術堆疊
- Python 3.11
- FastAPI
```

問題：

1. 每次開新 session，這個 CLAUDE.md 都一模一樣嗎？哪個部分會造成快取 miss？

   答：**時間戳** `更新於 2026-06-13 15:30`。時間戳每次開 session 都不一樣，第一行就已經和上次不同，整個 CLAUDE.md 全部 cache miss——後面再穩定的技術堆疊也都要重算。

2. 如果把時間戳移到底部，快取命中率會如何改變？

   答：頂部的技術堆疊、架構說明等穩定內容前綴完全一致，**這些部分命中快取**（折扣 90%）。只有底部的時間戳需要重算，快取命中區段從 0% 提升到約 80-90% 的 CLAUDE.md 長度。

3. 哪個結構快取命中率更高？原因是什麼？

   答：**結構 B**。前綴匹配從第一個字元開始——結構 A 的第一行就是時間戳（每次都變），第 1 個字元就 miss，整個文件全部重算。結構 B 的頂部是穩定的技術堆疊，前綴完全一致，只有底部動態部分 miss，穩定區完整享受快取折扣。

### 實際結果

理解 Exact Prefix Matching：一個字元不同就從那行開始全部重算。時間戳放頂部 = 永遠 0% 命中。移到底部 = 穩定區 90% 命中。結構 B 優於結構 A 的唯一原因：穩定內容在頂部。

## Step 3：檢查自己的 CLAUDE.md

### 操作步驟

1. 打開這個專案的 CLAUDE.md：

```bash
cat "c:/Users/user/workspace/kindle-20-65-automation-patterns/CLAUDE.md" | head -50
1``

1. 對照下方的分類標準，判斷現有 CLAUDE.md 的每個段落屬於哪一類：

| 類型 | 定義 | 應放在 |
|------|------|--------|
| 穩定內容 | 每次 session 都一樣，很少變動 | 頂部 |
| 半穩定內容 | 偶爾更新（每週/每月） | 中間 |
1 動態內容 | 每次 session 都可能不同 | 底部 |

1. 寫出你發現的問題（如果有）：

   答：這個專案的 CLAUDE.md 主要引用 `@instructions/` 模組，本身沒有時間戳或動態狀態——結構健康。常見錯誤是把「今天做到哪裡」或「目前卡在什麼 bug」寫進 CLAUDE.md 頂部；這些應放在 `memory/short-term/` 或 `context/hot-cache.md`，讓 CLAUDE.md 保持永久穩定。

| 類型 | 判斷 |
|------|------|
| 穩定 | 語言鐵律、技術堆疊偏好、全域原則 ✅ 在頂部 |
| 半穩定 | `@instructions/*.md` 引用清單 ✅ 在中段 |
| 動態（應移除） | session 狀態、今日 TODO、最新 commit → 不應在 CLAUDE.md |

### 實際結果

檢查 CLAUDE.md 確認：頂部是永久穩定的規則，沒有時間戳或動態狀態。結構符合快取最佳化原則。

## Step 4：設計理想的 CLAUDE.md 分層結構

### 練習

參考 `cache-design-guide.md` 的範本，設計一個你自己專案的 CLAUDE.md 理想結構：

```markdown
## ——— 穩定區（放頂部，最大化快取）———
- 專案目標與一句話說明
- 技術堆疊（框架版本、語言、資料庫）
- 程式碼撰寫慣例（命名規則、縮排、編碼）
- 全域禁止事項（不硬編碼路徑、不 INSERT 唯讀 DB 等）
- @instructions/ 模組引用

## ——— 半穩定區（放中間）———
- 目錄結構（新增大模組時才更新）
- 主要依賴套件清單（升版時才更新）
- 重大架構決策（一旦決定很少再變）

## ——— 動態區（放底部，每次都重算）———
- 不要有任何內容 ← 正確答案是「空的」
- 動態狀態 → memory/short-term/ 或 context/hot-cache.md
- 今日 TODO → task 系統，不放 CLAUDE.md
```

### 實際結果

設計三層結構：穩定區（技術堆疊/規範/禁令）+ 半穩定區（目錄/套件）+ 動態區（空白，動態內容全部外移）。核心原則：CLAUDE.md 不是工作日誌，是「永遠正確的專案說明書」。

## 本課重點

```
快取命中的唯一條件：
  本次送出的 Prefix == 上次送出的 Prefix（完全一樣，一個字元都不能差）

CLAUDE.md 分層策略：
  ✅ 頂部：技術堆疊、架構說明、命名規範（從不變）
  ⚠️ 中間：依賴套件版本、團隊規範（偶爾更新）
  ❌ 底部：今日 TODO、最新錯誤訊息、時間戳（每次都變）

最常見的快取殺手：
  - CLAUDE.md 頂部放時間戳
  - session 每次 import 不同的動態狀態
  - 系統提示包含環境變數（如當前時間）
```
