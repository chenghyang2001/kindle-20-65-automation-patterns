# 幻覺偵測指南

## 四個驗證提問

在實作前後向 Claude 提出以下問題。

```text
Q1：「請提供你在這次實作中使用的每個函式或方法的
    官方文件 URL 與對應章節。」
    → 如果 Claude 無法引用真實存在的 URL，請自行獨立查證。

Q2：「執行這段程式碼需要什麼版本？
    你有在官方文件中確認過這個限制嗎？」
    → 回答「我沒有查過」就是幻覺風險的信號。

Q3：「有沒有其他替代實作方式？各自的取捨是什麼？」
    → 說不出任何替代方案，可能代表理解狹隘或有誤。

Q4：「請舉出三個會讓這個實作失敗的情境或邊界案例。」
    → 說不出失敗案例，表示對這個實作的理解很淺。
```

## 七個紅旗訊號

```text
RF1：「應該是...」「大概...」「似乎...」
     → 把不確定的資訊當成事實來陳述。

RF2：沒有出處的數據
     → 「快 30%」「記憶體用量減半」— 沒有根據的效能數字。

RF3：新舊語法混用
     → 新版函式庫 API 混雜舊版語法。

RF4：不存在的選項或旗標
     → 實際上不存在的 CLI 旗標；無效的設定鍵。

RF5：與文件不符的錯誤訊息
     → 程式碼範例中的錯誤處理用了錯誤的例外類別名稱。

RF6：過度樂觀的描述
     → 實作說明完全沒提到限制、注意事項或失敗情境。

RF7：與先前回答互相矛盾
     → 同一個 session 內對同一主題給出不同的資訊。
```

## 幻覺應對流程

```text
偵測到紅旗訊號
  → 查閱 ~/.claude/docs/ 的本地文件
  → 無法確認 → 標記為「（待查證）」並暫緩
  → 發現矛盾 → 以正確資訊取代
  → 修正後，用 Q1–Q4 重新驗證
```

## 使用訣竅

- 四個提問採用「讓 Claude 驗證自己答案」的方式
- 七個紅旗訊號由人類審查者來觀察
- 只要出現「應該是...」，就養成查官方文件的習慣
- 幻覺不是能力缺陷 — 它是 LLM 的結構性特質
- 比起說「你的答案是錯的」，
  說「請到文件中查證這項資訊」能得到更準確的修正
