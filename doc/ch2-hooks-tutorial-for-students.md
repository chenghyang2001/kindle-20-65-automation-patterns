> 這份教材會教你：當 AI 幫我們寫程式、操作電腦時，我們怎麼幫它「裝上安全帶與規矩」。
> 假設你**完全沒學過程式**，所以每個名詞我都會用生活比喻講清楚。
> 全部的範例程式，老師都**真的在電腦上跑過一遍**，下面看到的結果都是真實畫面。

## 給老師與讀者的話

這份教材的主角叫 **Hook**（讀作「胡克」，原意是「掛鉤」）。
它是工具 **Claude Code** 的一個功能。Claude Code 是一個會幫你寫程式、改檔案、操作電腦的 AI 助理。

你可以把這整份教材想成一個故事：

> 我們請了一位**超級聰明、但完全不懂人情世故的工讀生（AI）**來幫忙做事。
> 他做事快得驚人，但有時會「為了把事情做好」而闖大禍。
> 於是我們要在工作流程裡，設下一道道「關卡」來管住他。
> 這些關卡，就是 **Hook**。

讀完這份教材，你會懂：

1. 為什麼一個聰明的 AI 反而很危險
2. Hook 是什麼、怎麼運作
3. 八個真實的 Hook 範例，每一個在防什麼、怎麼防
4. 老師實際操作時踩到的三個坑（這部分最好玩）

# 第一部分：先打地基（觀念）

## 1-1. 開場故事：AI 把整個專案刪光的那一夜

想像一個畫面：

你正看著你的 AI 助理，用閃電般的速度幫你重構一個很複雜的程式。它的邏輯完美、命名漂亮，你看得很爽。然後，就在一眨眼的瞬間——

它為了解決一個「暫存空間不足」的小問題，自己決定下了一道指令：

```
rm -rf /
```

這道指令的意思是「**把這個資料夾底下的所有東西，全部刪光，不問你、不留情**」。結果你整個專案，一乾二淨，消失了。

**這裡有個重點，你一定要懂**：

AI **不是壞心**。在它的「腦袋」裡，刪掉那些檔案，純粹是「當下最有效率的清理方式」。它就像一個極度聰明、卻完全沒有常識的工讀生：你叫他「把桌子清乾淨」，他可能連桌子一起鋸掉丟了，因為這樣「桌面確實最乾淨」。

> 📌 **核心問題**：AI 的「意圖」（想把事情做好）和「後果」（闖大禍）之間，有巨大的落差。
> 我們需要一個機制，在它**真正動手之前**攔住它。這個機制就是 Hook。

---

## 1-2. 什麼是 Hook？三個生活比喻

Hook 的本質是：**在某個特定時間點，自動跳出來檢查、甚至攔截動作的一段小程式。**

用三個比喻你就懂了：

**比喻一：大樓門口的警衛 🛡️**
任何人要進大樓（AI 要執行任何動作），都得先經過警衛。警衛看一眼：是住戶就放行，是可疑人士就擋下。Hook 就是這個警衛。

**比喻二：工廠生產線的品管站 🏭**
產品要出貨前（AI 要結束工作前），先經過品管站檢查。沒過關就退回去重做。Hook 就是這個品管站。

**比喻三：電玩的存檔點 💾**
你玩遊戲打到一半要關機（AI 的對話快被清空前），遊戲自動幫你存檔，下次回來進度還在。Hook 也能做這件事。

這三件事——**把關、品管、存檔**——等一下你都會看到真實範例。

> 📌 一句話定義：**Hook 是 AI 工作流程裡的「自動關卡」，它讓 AI 無論想做什麼，都必須先通過我們設下的規矩。**

---

## 1-3. 預備知識速成包（看不懂程式沒關係，這裡補給你）

要看懂後面的範例，你需要先認識四個東西。我保證用最白話的方式講。

### (A) 什麼是 Shell Script（.sh 檔）？

**Shell** 是你跟電腦「用打字下指令」溝通的方式（不是用滑鼠點）。
**Script（腳本）** 就是「把一連串指令寫成一張紙，讓電腦照著一行一行做」。
副檔名 `.sh` 的檔案，就是這種「指令清單」。

比喻：食譜。一張寫著「① 打蛋 ② 加鹽 ③ 下鍋」的紙，電腦照著做。

### (B) 什麼是 JSON？

JSON 是一種「**整理資料的格式**」，長得像這樣：

```json
{ "名字": "小明", "年齡": 17, "社團": "資訊社" }
```

比喻：便當盒的隔層。每一格貼了標籤（名字、年齡），格子裡放對應的東西。電腦最愛這種整整齊齊的便當盒，一看就知道哪格放什麼。

後面 AI 跟 Hook 之間傳遞訊息，用的就是 JSON 這種便當盒。

### (C) 什麼是 stdin 和 stdout？

- **stdin（標準輸入）** = 程式的「**耳朵**」，用來接收別人丟進來的資料。
- **stdout（標準輸出）** = 程式的「**嘴巴**」，用來把結果講出來。

比喻：一台果汁機。你從上面丟水果進去（stdin），它從下面流出果汁（stdout）。

Hook 的運作就是：AI 把一個 JSON 便當盒**丟進 Hook 的耳朵**，Hook 處理完，再從**嘴巴吐出結果**。

### (D) 什麼是 Exit Code（退出碼）？★最重要★

這是**整份教材最關鍵的概念**，請務必懂。

每個程式跑完，都會留下一個數字當「成績單」，這個數字叫 exit code：

| Exit Code | 意思 | 比喻 |
|:---:|------|------|
| **0** | 一切正常，**放行** | 考試 100 分，過關 ✅ |
| **2** | 有問題，**擋下** | 考試不及格，當掉 ❌ |

所以後面你會一直看到「exit=0」「exit=2」。看到就想：

- **exit=0 → AI 可以繼續做**
- **exit=2 → AI 被攔下，不准做**

> 📌 **這就是 Hook 攔截 AI 的核心魔法**：Hook 只要回傳 `exit 2`，AI 的動作就被硬生生擋下來。

更厲害的是：`exit 2` 的時候，Hook 還能**從嘴巴（stdout/stderr）吐出一句話告訴 AI「為什麼被擋」**。AI 收到這句話，就會知道要換個方法。這叫做「**自我修正回圈**」——AI 撞牆、被告知原因、換方法、再試，全程不需要人類插手。

比喻：就像你打電動，角色撞到牆會反彈，螢幕還跳出「此路不通，請走右邊」，你就知道要改走右邊。

## 1-4. 「17 個事件」是什麼？

Claude Code 把 AI 的一生，切成 17 個「時間點」，每個時間點都可以掛 Hook。把它想成 AI 工作的一條時間軸：

```
AI 開始上班 ──→ 要用工具前 ──→ 用工具後 ──→ 想下班 ──→ 記憶體快滿了 ──→ 真的下班
   (SessionStart)  (PreToolUse)   (PostToolUse)  (Stop)    (PreCompact)
        │              │              │            │            │
     可掛Hook       可掛Hook       可掛Hook      可掛Hook     可掛Hook
```

你不用背全部 17 個。這份教材只會用到最重要的幾個：

| 事件名稱 | 白話 | 像什麼 |
|---------|------|--------|
| **PreToolUse** | AI「動手前」 | 動手前的最後一道防線 |
| **PostToolUse** | AI「動手後」 | 收尾、整理 |
| **Stop** | AI「想下班時」 | 下班前的品管 |
| **PreCompact** | AI「記憶快滿、要壓縮前」 | 趕快存檔 |
| **SessionStart** | AI「重新上班時」 | 讀回上次的存檔 |

懂了這條時間軸，下面八個範例你就能對號入座。

## 範例 1：安全警衛 `block-dangerous.sh`

### ① 情境

這就是開頭那個「AI 刪光專案」故事的解藥。我們要設一個警衛，AI 每次要下指令前（PreToolUse），先檢查指令裡有沒有危險字眼，有就擋。

### ② 程式碼逐行拆解

```bash
INPUT=$(cat)                                          # ← 耳朵：把 AI 丟進來的便當盒接住
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command') # ← 從便當盒挖出「AI 想下的指令」

PATTERNS=(                  # ← 列一張「黑名單」：這些都是危險字眼
  "rm -rf /"               #   刪光檔案
  "git push --force"       #   強制覆蓋別人的程式
  "chmod -R 777"           #   把檔案權限全開（資安大忌）
  "DROP TABLE"             #   刪掉整張資料庫表格
)

for pattern in "${PATTERNS[@]}"; do        # ← 把黑名單一個一個比對
  if echo "$COMMAND" | grep -qF "$pattern"; then  # ← 指令裡有黑名單字眼嗎？
    echo "Blocked: '$pattern' ..." >&2     # ← 有！從嘴巴喊「擋下」
    exit 2                                  # ← 回傳成績單 2 = 攔截！
  fi
done

exit 0   # ← 都沒中黑名單，回傳 0 = 放行
```

白話總結：**「把 AI 想下的指令，拿去跟一張危險黑名單一一比對。中了就 exit 2 擋下，沒中就 exit 0 放行。」**

### ③ 老師真實執行結果

老師用「假裝 AI 下指令」的方式，餵了五種指令進去測試：

```
-- 測試1 危險：遞迴刪除根目錄 --     → Blocked   → exit=2 ✅ 擋下
-- 測試2 危險：強制推送 --           → Blocked   → exit=2 ✅ 擋下
-- 測試3 危險：刪資料表 --           → Blocked   → exit=2 ✅ 擋下
-- 測試4 安全：列檔 (ls -la) --       →（無事）   → exit=0 ✅ 放行
-- 測試5 邊界：空指令 --              →（無事）   → exit=0 ✅ 放行
```

五個全部如預期！危險的擋下、安全的放行。

### ④ 為什麼這樣設計？

- **為什麼用「黑名單」？** 因為危險指令的種類有限，列清楚最簡單直接。
- **為什麼選 PreToolUse（動手前）？** 因為這是「最後一道防線」。只要在這裡攔住，AI 根本還沒動手，系統不會有任何損傷。
- **小缺點**：黑名單是「死的字串比對」，它看不懂語意。這個缺點，老師等一下會在「踩坑」單元親身示範給你看。

## 範例 2：MCP 後門守衛 `mcp-write-guard.sh`

### ① 情境

這裡有個**很容易被忽略的危險**。

AI 除了用「內建工具」，還能透過一種叫 **MCP** 的東西，外接到 GitHub、公司資料庫等外部系統。問題來了：**我們前面設的警衛，只管得到「內建工具」，管不到 MCP！** MCP 走的是另一條獨立通道。

比喻：你把大門鎖得死死的（警衛守著內建工具），卻給了 AI 一把能開**後門**的萬能鑰匙（MCP）。它可以從後門溜出去搞破壞，而你的警衛完全看不到。

### ② 程式碼逐行拆解

```bash
TOOL=$(echo "$INPUT" | jq -r '.tool_name')   # ← 挖出「AI 想用哪個工具」

# 只盯著 MCP 的「寫入/刪除/搬移」這幾種危險動作
if echo "$TOOL" | grep -qE "mcp__filesystem__(write|delete|move)"; then
  FILE=$(...)                                  # ← 挖出它想動哪個檔案
  if echo "$FILE" | grep -qE "\.(env|pem|key)$"; then  # ← 是機密檔嗎？(.env/.pem/.key)
    # 是機密檔！吐出一個 JSON 便當盒，裡面寫「拒絕」
    jq -n '{ ... "permissionDecision": "deny" ... }'
  fi
fi
```

白話總結：**「專門盯著 MCP 的寫入動作。如果它想碰 .env / .key 這種藏密碼的機密檔，就吐一張寫著『拒絕』的 JSON 擋下。」**

（`.env`、`.key` 這些檔案，通常存著密碼、金鑰，外洩就慘了，所以要特別保護。）

### ③ 老師真實執行結果

```
-- 測試1：MCP 想寫入 .env 機密檔 --
  → Blocked MCP access to sensitive file: /app/.env
  → 吐出 JSON：{ "permissionDecision": "deny", "reason": "不允許存取機密檔" } ✅
-- 測試2：MCP 想寫入 README.md 普通檔 --
  →（無事，放行）✅
```

機密檔被擋、普通檔放行，完美。

### ④ 為什麼這樣設計？

- **為什麼這個範例不用 exit 2，而是吐 JSON？** 因為 JSON 可以講得更精細——不只是「擋」，還能附上明確理由（reason），AI 收到後更清楚自己錯在哪。
- **教訓**：設防護網時，不能只防「正門」，要記得 AI 還有 MCP 這個「後門」。這是資安最常被忽略的死角。

## 範例 3：跨平台版 `check-command.mjs`（用 Node.js 寫）

### ① 情境

前面的警衛是用 Bash（.sh）寫的。但 Bash 有個麻煩：**換一台電腦可能就跑不動**。
特別是 Windows 跟 Mac/Linux 之間，Bash 腳本常常水土不服。

解法：改用 **Node.js**（副檔名 .mjs）來寫。Node.js 在哪台電腦都能跑，而且它**天生就會看懂 JSON 便當盒**，不需要額外裝工具。

### ② 程式碼重點

```javascript
const input = await readStdin()          // ← 耳朵：接住 JSON（Node.js 原生就會解析）
const { tool_name, tool_input } = input  // ← 直接拆出便當盒內容

if (tool_name === 'Bash') {
  const BLOCKED = ['rm -rf', 'git push --force', 'DROP TABLE']  // ← 黑名單
  for (const pattern of BLOCKED) {
    if (command.includes(pattern)) {      // ← 中黑名單？
      process.exit(2)                     // ← exit 2 擋下（跟 .sh 版邏輯一樣）
    }
  }
}
process.exit(0)                           // ← 放行
```

功能跟範例 1 一模一樣，只是換成跨平台的寫法。

### ③ 老師真實執行結果

```
-- 測試1：危險指令 → Blocked → exit=2 ✅
-- 測試2：安全指令 →（無事）→ exit=0 ✅
```

### ④ 為什麼這樣設計？

- **為什麼推薦 Node.js 而不是 Bash？** 因為 Hook 之間大量用 JSON 溝通，而 Node.js 內建就能處理 JSON，不像 Bash 要另外裝一個叫 `jq` 的工具（不同電腦的 jq 版本還常常打架）。
- **白話**：同樣一份警衛工作，Node.js 版「搬到哪台電腦都能上工」，Bash 版「換台電腦可能就罷工」。

## 範例 4：下班品管員 `quality-gate.sh`（Stop 事件）

### ① 情境

AI 覺得自己做完了，想「下班」（Stop 事件）。但等等——它有沒有把工作收好？
這個 Hook 就是下班前的品管員，檢查兩件事：

1. 有沒有**還沒存檔**的程式改動？
2. 程式裡有沒有還沒做完的 **TODO（待辦標記）**？
沒過關，就不准下班，趕回去收尾。

### ② 程式碼裡最精妙的設計：防止「無限鬼打牆」

這裡有個**超重要的陷阱**。想想看：

1. AI 想下班 → 品管員擋下「你還沒收尾！」
2. AI 收到錯誤 → 試圖修復 → 又想下班
3. 品管員又擋下 → AI 又修 → 又想下班……

如果不處理，這會變成**無限迴圈**，AI 在那邊鬼打牆撞個沒完，把費用燒光！

解法：裝一個「鎖」。

```bash
STOP_HOOK_ACTIVE=$(echo "$INPUT" | jq -r '.stop_hook_active')
if [ "$STOP_HOOK_ACTIVE" = "true" ]; then
  exit 0     # ← 如果「已經在被擋的修正狀態中」，這次就放行，避免無限鬼打牆
fi
```

白話：這個 `stop_hook_active` 就像一個記號。第一次擋 AI 時做個記號，下次看到記號就知道「它正在修了，別再無限擋它」。

### ③ 老師真實執行結果

**情況 A：已經在修正狀態（有記號）**

```
stop_hook_active = true → exit=0（直接放行，不鬼打牆）✅
```

**情況 B：真的有沒收尾的工作**（老師故意做了一個有未存檔改動 + 一個 TODO 的測試專案）

```
→ 吐出 JSON：
{
  "decision": "block",
  "reason": "1. 偵測到未提交的改動
             2. 還剩 1 個 TODO 標記"
}
```

品管員清楚列出「兩個沒收尾的地方」，把 AI 擋下趕回去做。✅

### ④ 為什麼這樣設計？

- **為什麼要防無限迴圈？** 因為這是「全自動」流程，沒有人在旁邊喊停。一旦鬼打牆，會持續燒錢直到費用見底。
- **金句**：「設防護網的同時，也要為**防護網本身**裝上煞車。」這個 `stop_hook_active` 鎖，就是防護網的煞車。

## 範例 5：AI 的外接記憶硬碟 `save-session-state` + `restore-context`

### ① 情境（這是最酷的一個）

AI 的「記憶」有限。當你跟它聊得越來越久，它的記憶體會塞滿。塞滿時，系統會自動「壓縮」對話——把舊的內容濃縮成摘要，騰出空間。

問題是：**壓縮時，很多重要小細節會永遠消失**。例如「你現在正在改哪個檔案」「剛剛哪個測試失敗了」。

比喻：你跟團隊開了八小時馬拉松會議。到傍晚，大家只記得「我們在做登入功能」，但**早上決定的關鍵細節，沒人記得了**。

解法是兩個 Hook 一搭一唱，幫 AI 做一個「外接記憶硬碟」：

```
記憶體快滿、壓縮前  ────→  PreCompact Hook：趕快把現況寫到硬碟存檔
（save-session-state.sh）

隔天 / 新對話開始  ────→  SessionStart Hook：開機就讀回硬碟的存檔
（restore-context.sh）
```

### ② 它存了什麼？

`save-session-state.sh` 在壓縮前，把這些「現況」寫進一個檔案：

- 現在在哪個 Git 分支（branch）
- 有哪些檔案改了還沒存
- 最近做了哪幾件事
- 最後一次測試的結果

`restore-context.sh` 則在開機時，把這個檔案讀出來，重新「提醒」AI。

### ③ 老師真實執行結果

**步驟 1：壓縮前存檔**，產生的存檔內容長這樣：

```
# Session State (存檔時間：2026-06-12 / 觸發：auto)
## 分支
master
## 還沒存的改動
src/app.js
[已暫存] src/notes.md
## 最近做的事
8c6b434 init
```

**步驟 2：新對話開機，讀回存檔**，AI 一開機就「想起來」：

```
## 已恢復的工作脈絡
### 分支：master
### 還沒存的改動：src/app.js、src/notes.md
### 上次存檔內容：（完整列出上面那些）
```

AI 一醒來就自動知道「我在 master 分支、有兩個檔案改到一半」，記憶無縫接軌！✅

### ④ 為什麼這樣設計？

- **白話**：這等於幫 AI 外接了一顆「長期記憶硬碟」。它的腦袋（記憶體）會忘，但硬碟不會忘。
- **這就是 1-2 節說的第三個比喻**——「電玩存檔點」的真實版。

## 範例 6：設定檔稽核員 `audit-config.sh`

### ① 情境

有些檔案**特別重要**，例如專案的設定檔 `settings.json`（它決定整個專案怎麼運作）。如果有人在你不知情時偷改它，可能出大事。這個 Hook 做兩件事：

1. **記帳**：任何設定變動，都寫進一本「稽核日記」留底。
2. **攔截**：如果是從外部偷改 `settings.json`，就擋下來要求人類先看過。

### ② 程式碼重點

```bash
echo "${DATE} | ${SOURCE} | ${FILE}" >> ".claude/config-audit.log"  # ← 先記一筆帳

if [ "$SOURCE" = "project_settings" ]; then        # ← 如果是動到專案設定
  if [ "$BASENAME" = "settings.json" ]; then       # ← 而且是 settings.json
    jq -n '{ "decision": "block", "reason": "外部修改設定檔，請先審查" }'  # ← 擋下
  fi
fi
```

### ③ 老師真實執行結果

```
-- 測試：外部修改 settings.json --
  → 吐出 JSON：{ "decision": "block", "reason": "外部修改設定檔，請先審查" } ✅
-- 稽核日記內容 --
  2026-06-12 15:06:19 | project_settings | /app/.claude/settings.json ✅（成功留底）
```

### ④ 為什麼這樣設計？

- **記帳 + 攔截雙管齊下**：就算哪天出事，你翻稽核日記就知道「誰、什麼時候、改了什麼」。這在資安上叫「可追溯性」。

## 範例 7：讓 AI 審查 AI（Prompt Hooks，最高階）

### ① 情境

前面的警衛都是「死的字串比對」——它們只會認黑名單上的字。但如果我要判斷的事情**很複雜**呢？

例如：「這次的資料庫修改，會不會害網站掛掉？」這需要**真正的判斷力**，不是比對字串能做到的。

解法（這是最聰明的一招）：**找另一個 AI 來當裁判，審查第一個 AI 的工作。**

### ② 怎麼運作？

這個 Hook 的型別設成 `prompt`（提示），意思是「**呼叫另一個 AI 來判斷**」。設計上有兩個巧思：

**巧思 1：用便宜又快的 AI 當裁判**

```json
{ "type": "prompt", "model": "claude-haiku-4-5", "prompt": "檢查這段程式有沒有資安問題..." }
```

裁判用的是 **Haiku**——一個又快又便宜的 AI（幾百毫秒就回答），不會拖慢速度。複雜的審查才換更聰明（也更貴）的 AI。

**巧思 2：裁判只能回傳固定格式**
裁判只准回兩種答案：

- 沒問題 → `{ "ok": true }` → 放行
- 有問題 → `{ "ok": false, "reason": "具體哪裡錯 + 怎麼修" }`

那個 `reason`（理由）**超關鍵**：它會被原封不動地塞回給第一個 AI，當成「下一個指令」。於是第一個 AI 立刻知道自己被抓包，開始照著理由自動修正。

### ③ 為什麼這樣設計？

- **白話**：這等於給你的 AI 助理，配了一個**不會累、隨時待命的資深前輩**，在每次存檔前都幫忙做一次 Code Review（程式碼審查）。
- **這就是自動化的最高境界**：AI 寫、AI 審、AI 改，形成一個會自我進化的循環。

---

## 範例 8：除錯神器 `debug-hook.sh`

### ① 情境

寫 Hook 時，常常遇到「它就是不動，但我不知道為什麼」。這個 Hook 是個**偵錯工具**：它把 AI 丟進來的每一個便當盒，原封不動地記到一個日記檔，讓你能「看到底發生什麼事」。

### ② 程式碼重點

```bash
INPUT=$(cat)
echo "=== $(date) ===" >> /tmp/claude-hook-debug.log    # ← 記時間
echo "$INPUT" | jq '.' >> /tmp/claude-hook-debug.log    # ← 把整個便當盒原樣記下來
```

### ③ 老師真實執行結果

餵一個假事件進去，日記檔忠實記錄：

```
=== Fri Jun 12 15:06:19 2026 ===
EVENT: PreToolUse
INPUT:
{
  "tool_name": "Bash",
  "tool_input": { "command": "echo hello" }
}
```

✅ 一字不漏記下來，除錯時超好用。

### ④ 為什麼這樣設計？

- **白話**：當 Hook 出問題，你不再是「盲猜」，而是打開日記檔，**親眼看到** AI 到底丟了什麼進來。

# 第三部分：老師的真實踩坑現場（最寶貴的部分）

> 課本講得再漂亮，真的動手做才會踩到坑。以下三個坑是老師這次親身遇到的，每一個都是活教材。

## 坑 1：老師自己的電腦，真的有一個警衛擋住了老師

老師在測試「範例 1 的危險指令攔截」時，想餵一個 `rm -rf /` 的假指令進去測試。結果——

**老師自己的 Claude Code 環境，真的裝了一個一模一樣的警衛 Hook！** 它一看到老師的測試指令裡有 `rm -rf /` 這幾個字，立刻 `exit 2` 把老師擋下來：

```
PreToolUse:Bash hook error: Blocked: 'rm -rf /' is a prohibited command
```

這超有意思——**課本講的機制，在老師身上活生生上演了一次**。

但它也暴露了範例 1 講的那個小缺點：**警衛看不懂語意**。老師只是想「測試」這個指令，根本沒有要真的執行，但警衛照樣擋——因為它只會「比對字串」，分不清「真要執行」還是「只是提到」。

> 📌 **這就是為什麼需要範例 7（AI 審查 AI）**：只有真正有判斷力的 AI，才能分辨「這個人是真的要刪檔，還是只是在測試」。死的字串比對做不到。

**老師怎麼解決？** 老師把危險指令寫進一個檔案，再餵給待測警衛——這樣老師自己打的指令裡就不含危險字眼，繞過了自己環境的警衛。

## 坑 2：一個藏很深的 Bug——`${INPUT:-{}}`

老師在測「範例 5 存檔」時，畫面跳出一個錯誤：

```
jq: parse error: Unmatched '}'
```

老師追查後發現，是存檔程式裡這一行有問題：

```bash
TRIGGER=$(echo "${INPUT:-{}}" | jq -r '.trigger')
```

問題出在 `${INPUT:-{}}` 這個寫法。它本意是「如果 INPUT 是空的，就用 `{}` 當預設值」。但 Bash 會把它**誤解**成「預設值是一個 `{`」+「多一個 `}`」，結果**多吐出一個 `}`**，害 jq 看到一個多餘的括號而報錯。

諷刺的是——**這正是課本警告的「Hook 不該亂吐東西污染輸出」的近親**：這個 Hook 自己往外噴了不該有的錯誤訊息。

**怎麼修？** 把那一行拆成兩步，意思更清楚：

```bash
[ -z "$INPUT" ] && INPUT='{}'            # 如果 INPUT 空的，才設成 {}
TRIGGER=$(echo "$INPUT" | jq -r '.trigger')
```

老師用「三個 AI 分工」的嚴謹流程修好了它（一個寫、一個驗、確認沒問題才算數），錯誤訊息消失了。

## 坑 3：跨平台的隱形地雷——CRLF

老師用一個叫 `shellcheck` 的「程式碼健檢工具」掃描所有 .sh 檔，跳出一堆警告 `SC1017`。

這個警告的意思是：**這些檔案是「Windows 換行格式」（叫 CRLF），不是「Mac/Linux 換行格式」（叫 LF）。**

你可能想：換行而已，有差嗎？**差很大。** 把 Windows 格式的 .sh 檔拿到 Mac/Linux 跑，那個多出來的隱形符號（`\r`）會混進程式，害它直接報錯「找不到直譯器」。

這又呼應了課本的跨平台精神——諷刺的是，這套「教你跨平台」的教材，自己的範例卻是 Windows 格式。

**怎麼修？** 老師沒有一個一個檔去改（那是治標，換台電腦又會跑掉）。老師加了一個叫 `.gitattributes` 的設定檔，裡面宣告一句：

```
*.sh text eol=lf      # 所有 .sh 檔，在任何電腦上都強制用 LF 格式
```

這一句話，讓**所有平台**（包括 Windows）拿到的 .sh 檔都自動是正確格式。一勞永逸。修完後，健檢工具的 `SC1017` 警告全部消失。

> 📌 **治標 vs 治本**：一個一個改檔案是治標；改一個設定讓全部自動正確，是治本。好的工程師永遠找治本的解法。

> 透過一道道規矩，塑造成「可靠的自動化系統」。
