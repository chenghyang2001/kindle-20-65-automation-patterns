# Claude Code 設計基礎實戰教學（讓 AI 不再變笨）

> **對象**：剛進職場的軟體工程師。
> 假設你會用 AI 對話寫程式，但常遇到「AI 聊著聊著就變笨」的困擾。
> 這份教材是整個系列的**地基**——教你如何設計專案，讓 AI 從「容易困惑、頻頻出錯的實習生」，變成「神級結對程式設計夥伴」。
> 所有範例老師都實際跑過，下面的執行結果是真實輸出。

---

## 寫在前面：為什麼 AI 聊著聊著就變笨了？

你一定遇過這個情境：

> 剛開始的 10 分鐘，AI 簡直像個天才，完美理解你的意圖、寫出乾淨俐落的架構，你甚至覺得今天可以提早下班。但隨著對話越來越長、視窗內容越積越多，它好像變了——忘記你們團隊剛講好的程式碼規範、一直犯同樣的錯，最後甚至憑空捏造根本不存在的 API。你坐在螢幕前抓狂：「為什麼這傢伙突然變笨了？」

**真相是：這不是 AI 模型能力到了極限，也不是它在偷懶。** 是我們作為「駕駛員」沒有好好管理 AI 的**注意力與記憶體**。當上下文塞滿一堆無關緊要的細節，再聰明的模型也會在雜訊中迷失方向——也就是產生**幻覺**。

這份教材（出自《Claude Code in Production》第一章）的核心思想只有一個詞：**關注點分離（Separation of Concerns）**。我們要學會把對的資訊放在對的地方，讓 AI 的龐大算力 100% 集中在你當下真正需要解決的痛點上。

# 第一部分：三層設定（出遠門的行李分類）

很多開發者習慣把所有資訊塞進同一個超大檔案——所有團隊規範、所有細節，全丟進一個全域設定檔。**這正是問題所在。** 我們必須根據資訊「被讀取的行為模式」，建立三個層級。

用「出遠門打包行李」來理解：

| 層級 | 位置 | 行李比喻 | 何時載入 |
|------|------|---------|---------|
| **CLAUDE.md** | 專案根/子目錄 | 穿在身上的**衣服** | 永遠掛在背景 |
| **Rules（規則）** | `.claude/rules/` | 背包底層的**雨傘** | 碰到特定副檔名才撐開 |
| **Skills（技能）** | `.claude/skills/` | **急救箱** | 明確下令或情境吻合才喚醒 |

## 第一層：CLAUDE.md（衣服——永遠穿著，不能太笨重）

CLAUDE.md 是專案的「環境音」——只要你啟動對話，它的內容就**永遠掛在背景**。

這帶來一個致命問題：你每問一個超簡單的問題（「幫我寫個正則表達式」），它都在默默吃掉 token，更糟的是**大量佔用 AI 寶貴的注意力**。

> 所以 CLAUDE.md 裡**絕對不能放瑣碎細節**。只適合放 AI 在這個專案隨時隨地都必須知道的**絕對事實**：全域架構邊界、核心命名慣例、關鍵檔案的絕對位置。
>
> 衣服不能穿太笨重，不然會走不動。

## 第二層：Rules（雨傘——下雨才拿出來）

特定語言的寫法該放這裡。它是**條件式載入**——透過 frontmatter 指定路徑條件（範例 `rules/coding-conventions.md`）：

```yaml
---
paths: ["src/api/**/*.ts"]
---
# API Development Rules
- Include input validation in every endpoint
- Use `ApiError` type for all error responses
```

只有當你開啟 `src/api/**/*.ts` 檔案時，這條 API 規則才啟動。你在編輯 Python 時，它**連半個 token 都不會佔用，AI 甚至根本不知道有這些規則存在**——直到真正需要的那一刻。雨傘平常收在背包底層，下雨才撐開。

## 第三層：Skills（急救箱——隨需呼叫）

技能是放在 `.claude/skills/` 的自動化腳本或任務流程，平常**絕對不消耗常駐 context**。只有當你明確下令、或 AI 從對話脈絡判斷情境極度吻合時，才被喚醒。

> 你絕對不會沒事把急救箱拿在手上逛街。只有真的有人受傷、需要執行某個醫療程序時，才會打開它。

**結論**：如果你不懂分類，把雨傘、急救箱全硬塞進外套口袋——難怪 AI 走不動、開始胡言亂語。

# 第二部分：CLAUDE.md 的進階組織

## @import 拆分（穩定 vs 變動分開存放）

當專案變大，CLAUDE.md 也會塞爆。用 `@import` 語法把內容拆出去（範例 `import-example/CLAUDE.md`）：

```markdown
- Git workflow: @docs/git-workflow.md
- API design conventions: @docs/api-conventions.md
- Testing guidelines: @docs/testing-guidelines.md
```

把穩定的架構決策、和容易變動的測試框架約定**分開存放**——修改一個就不會弄壞另一個。（`CLAUDE.local.md` 會自動進 .gitignore，放個人設定。）

## Monorepo 向上遍歷（作用域 Scope）

如果你的是 monorepo（一個 repo 下有前端 React、後端 Go、資料庫團隊），每個團隊風格不同——前端用 4 格縮排、後端用 Tab。全寫進一個規則 AI 會精神分裂。

解法是**向上遍歷**，就像程式裡的「作用域」。範例 `monorepo-example/` 在 root、`packages/frontend`、`packages/backend` 各放一個 CLAUDE.md。

**老師的實跑驗證**（模擬 AI 在 `packages/frontend` 工作時的載入順序）：

```
情境：AI 正在 packages/frontend/ 改 code

AI 載入順序（先具體後全域）：
  1. packages/frontend/CLAUDE.md  「Frontend Package」  作用域最大（最優先）
  2. (root)/CLAUDE.md             「Monorepo: my-project」 全域底線（天條）
```

它先讀前端資料夾的 CLAUDE.md，再往上找根目錄。**越具體的資料夾權限越大**：


- 根目錄放全公司天條（Conventional Commits、不可在 `packages/` 下直接建檔）
- 前端資料夾的排版風格設定可直接覆寫根目錄

這樣資料庫團隊寫 SQL 時，**永遠不會被前端的 React 規範干擾**（作用域隔離）。

# 第三部分：描述陷阱（本章最反直覺的一課）

技能是「隨需呼叫的急救箱」——但 AI 怎麼知道何時該把急救箱拿出來？它又沒裝監視器。

答案藏在技能的 `description`（描述）欄位。而這正是**無數開發者最常踩的陷阱**。

## 致命的錯誤：把描述當執行手冊

很多工程師定義技能時，會在描述裡洋洋灑灑寫滿執行細節（範例 `bad-example.md`）：

```yaml
description: >
  Deploy skill.
  1. Run npm test and confirm all tests pass
  2. Build with npm run build
  3. Deploy with git push origin main      ← 把「怎麼做」寫進描述
  4. Verify deployment ...
```

在傳統程式設計裡，「描述越詳細越好」是對的。**但在 LLM 的世界，這是致命傷。**

## 為什麼？描述是「語意選擇器」不是「執行手冊」

對 AI 來說，描述欄位的功能是**語意選擇器**——Claude 透過閱讀描述，決定「我要不要在這個時間點載入這個技能」。它把描述當成**觸發條件**，不是執行手冊。

> 如果你把執行步驟寫在描述裡，Claude 看完會產生錯覺：「哦，你已經告訴我該怎麼做了（test→build→push）。」於是它**根本不去載入技能的真正實作腳本**，直接靠自己的千億參數大腦開始猜測——然後產生幻覺。

**餐廳點餐比喻**：如果選單把「大蒜炒義大利麵」的每個烹飪步驟都印在菜名底下，服務生看完可能直接在你桌邊開始切大蒜炒麵，根本不把訂單交給後廚——整間餐廳大亂。

> **描述 = 點餐介面**（讓 AI 知道有這道菜）；**技能主體 = 廚房實作**（真正的後台邏輯）。必須明確區分「這道菜是什麼」和「這道菜怎麼做」。

## 完美的描述怎麼寫？

只需要兩部分（範例 `good-example.md`）：

```yaml
description: >
  Run a code review. Handles PR reviews, code checks, quality checks,
  security audits, and bug detection. Responds to requests like
  "review this code", "check this PR", "what do you think of this code?".
```

1. **簡短一句說明做什麼**
2. **明確指出何時使用（觸發情境）**——而且**故意塞滿同義詞**

## 為什麼要塞同義詞？

因為 AI 匹配技能的底層機制**不是死板比對精確關鍵字，而是透過向量嵌入計算語意相似度（算數學距離）**。

當使用者說「幫我看一下這包 code 能不能 merge」，AI 把這句話轉成數學向量，去跟技能描述的向量比對。如果你只寫「review PR」，在數學空間裡「merge」可能離得太遠，AI 就**錯過了這個急救箱**。

> 你必須提供足夠的「**表面積**」——把人類在自然對話中可能用到的各種口語說法都寫進去，給 AI 的語意雷達一個更大的目標去鎖定。

# 第四部分：高風險技能的安全控制

有些技能很危險（一鍵部署正式環境、清理資料庫）。如果 AI 在語意判斷時稍微手滑自己啟動，會是災難。兩個關鍵 frontmatter 標籤：

| 標籤 | 範例 | 效果 |
|------|------|------|
| `disable-model-invocation: true` | `deploy.SKILL.md` | **人類守門員機制**。對部署/改資料庫這類破壞性行為，技能變成「唯讀展示品」——AI 看得到、知道有這工具，但**絕對無法自動觸發**，必須人類親自手動輸入指令才能按下發射鈕 |
| `user-invocable: false` | `legacy-context.SKILL.md` | 純背景參考資料（如遺留系統的瑣碎約束）。AI 遇到相關工作會自動參考，但**從人類選單隱藏**，保持操作介面清爽 |

> 該鎖的鎖起來，該藏的藏起來。

# 第五部分：子代理——派研究助理去地下室

假設你要 AI 對一個包含 50 個檔案的龐大專案做安全審查。如果直接在對話視窗執行——AI 會開啟這 50 個檔案、把程式碼全讀進來，瞬間消耗數千甚至上萬 token。

更嚴重的是引發 LLM 惡名昭彰的 **「迷失在中間（Lost in the Middle）」效應**：上下文塞太滿時，AI 的注意力機制開始失效，它只記得開頭和結尾、忘記中間細節。這 50 個檔案的內容會**徹底汙染你的對話脈絡**，接下來你問任何問題，它都帶著這些雜訊回答——開始精神錯亂。

## 解法：context: fork

在技能設定加上 `context: fork`（範例 `subagent-skill/SKILL.md`）：

```yaml
name: security-audit
context: fork      ← 分岔出獨立、乾淨的子代理
agent: Explore     ← 確保唯讀，絕不亂改程式
allowed-tools: Read, Grep, Glob
```

> **老闆派助理比喻**：你是日理萬機的老闆，不想為了查一個歷史資料親自跑去滿是灰塵的地下室、把辦公室弄亂。所以你派一個專門的研究助理（子代理）去地下室，規定它**只能看不能改**（唯讀模式），它在下面查完後，只把**一頁重點報告**放到你桌上就好。

這樣你的大腦（主 context）保持極度清晰、專注決策。不只省了海量 token，更完美保護了 AI 的注意力——把繁重的資料提取工作外包，只保留高密度的決策資訊。

# 第六部分：給靜態檔案注入生命力（動態上下文）

前面的設定檔、技能檔切得再細，終究都只是**靜態的文字檔**。但寫程式是動態過程——如果你剛切換了 git 分支、終端機剛跑出三個失敗測試，AI 怎麼會知道？難道每次都要手動複製貼上最新 log？那算什麼自動化。

## 神奇語法：`!​`command``

範例 `dynamic-context/SKILL.md` 用「驚嘆號 + 反引號包圍指令」：

```markdown
- Branch: !`git branch --show-current`
- Recent commits: !`git log --oneline -3`
```

運作機制：在你的提示詞**真正送給 Claude 看到之前**，系統在底層攔截這個動作，先開一個子終端機執行這段指令，把指令字串**直接替換成熱騰騰的真實結果**，最後才送給 Claude。

**老師的實跑驗證**：

```
── 靜態 SKILL 模板 ──
- Branch: !`git branch --show-current`
- Recent commits: !`git log --oneline -3`

── 注入引擎執行後（AI 實際看到的）──
- Branch: main
- Recent commits: 49d67c1 新增 ch5 權限與安全教學; e1708db 新增 ch4 CI/CD 教學; ...
```

> 對 Claude 而言，它根本不知道我們在底層偷偷跑了腳本。它一睜開眼，看到的就是一份**已經填滿當下最新狀態的報告**。這等於給 AI 裝上了**即時感測器**，而且完全不浪費 AI 呼叫工具來回溝通的思考時間。

# 第七部分：終極魔王——上下文壓縮（記憶刺青）

當你和 AI 進行好幾小時的深度除錯，終究會遇到無法迴避的物理限制：**上下文壓縮（Context Compression）**。當對話逼近上限，Claude 為了能繼續對話，必須自動壓縮早期記錄來釋放空間。

問題是：壓縮時，那些你以為它該記住的關鍵進度，往往被當成雜訊丟棄——這就是「它失憶了」的真相。

## 但壓縮是可以被控制的

在 CLAUDE.md 加入 **Compact Instructions（壓縮指示）** 區塊（範例 `compact-instructions.md`）：

```markdown
## Compact Instructions
When compressing context, always preserve:
- Full paths of all modified files
- Bugs discovered and planned fixes
- Design decisions made during this session
- Incomplete tasks (what remains to be done)
```

> 我們不再消極地祈禱 AI 記住重點，而是**下達「保留重要物資」的鐵令**。自動壓縮不是災難，而是可以被控制的最佳化過程。

**《記憶拼圖》比喻**：電影主角知道自己每隔一段時間就會完全失憶，所以在失憶前，把最重要的線索狠狠刺青在身上。Compact Instructions 就是我們給 AI 刺上的刺青——確保下一個週期的它醒來時，看照身上的文字就絕對不會迷失方向。

（可搭配 PreCompact Hook 在壓縮前把狀態存到檔案，雙重保險。）

## 最後一塊拼圖：專案模板

為了不讓每次開新專案都重新經歷「刺青」的痛苦設定，把調校好的設定檔存在 `.claude/templates/`（範例有 `nextjs/go/django`）。重點是可以把**團隊的地雷區**寫進模板的 **prohibited patterns（禁止模式）**：

```markdown
- 本專案絕對不要使用過時的 pages router
```

預防勝於治療——與其讓 AI 寫出舊版程式碼、你再糾正它浪費 token，不如一開始就把坑填了，阻止它去嘗試註定失敗的路徑。

# 結語：你在為機器寫文件，也在為人類寫入職指南

我們從三層設定檔出發，破解了描述陷阱，學會用唯讀子代理隔離工作區，到動態指令注入與記憶刺青。這一切本質上都在做同一件事——**關注點分離**：

| 分離 | 目的 |
|------|------|
| 常駐記憶 vs 條件載入 vs 隨需呼叫 | 降低環境負擔 |
| 點餐介面 vs 廚房實作 | 讓 AI 正確載入技能 |
| 主代理 vs 子代理 | 保護主 context 的注意力 |

當我們幫 AI 濾掉不必要的雜音，它的龐大算力才能 100% 集中——**讓它專注，它才能展現天才的一面**。

## 留給你的思想實驗 🤔

如果我們把 CLAUDE.md 和各種規則寫得如此精煉完美——精準捕捉了專案架構、團隊約定、甚至那些「千萬不要這麼做」的血淚教訓——以至於連一個沒有任何人類直覺、只懂數學機率的 AI 都能立刻進入狀況、產出高品質程式碼……

> 那麼這份我們為了**機器**精心打造的文件，
> 難道不也是給**人類新進員工**最完美的一份入職指南嗎？

當你在定義「專案的物理定律」時，其實也在逼自己檢視團隊的規範是不是一團亂——你在學著成為更清晰、更有條理的溝通者。

所以下次開新專案時，試著把你的 AI 當作「你見過最聰明、運算最快、但同時也最容易分心的新同事」來設定吧：**把行李分好類、給它明確的選單、派它去地下室找資料、並在它失憶前幫它留下備忘錄。** 你會發現，當你學會引導這個數位大腦時，受益的不只是 AI 的效能，還有你**掌控複雜系統的思維高度**。
