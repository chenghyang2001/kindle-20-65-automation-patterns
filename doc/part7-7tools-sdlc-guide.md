# 給初階工程師的七工具 × 軟體開發流程整合指南

> **對象**：剛進入軟體開發職場、開始使用 Claude Code 的工程師  
> **目標**：理解 Claude Code 的 7 個進階工具如何貫穿完整開發週期，以及為什麼要在「對的時機」使用「對的工具」  
> **前提**：你已知道 Claude Code 的基本操作（能開啟、能執行 Skill、能用 /slash 命令）

---

## 前言：為什麼需要這 7 個工具？

假設你剛接到一個任務：「幫我加一個折扣碼功能到購物車。」

如果你直接告訴 Claude Code「開始寫吧」，最常見的後果是：

1. **幻覺 API**：AI 引用了一個不存在的套件方法，你 copy 貼上後執行才發現錯誤
2. **主分支汙染**：開發做到一半發現方向不對，但改動已經混入 main
3. **沒有測試**：功能「看起來」通過，但沒有任何測試保護，三週後改動其他模組時悄悄壞掉
4. **重複造輪子**：花兩天寫了一個折扣計算器，後來才發現開源套件早就做好了

這 7 個工具就是為了系統性地消滅上述問題而存在。它們不是獨立功能，而是一條**從「接任務」到「知識傳承」的完整防護鏈**。

---

## 軟體開發的 7 個關鍵時機

```
任務進來 → 需求分析 → 設計規劃 → 實作開發 → 審查測試 → 部署收尾 → 持續學習 → 知識傳承
    L3         L1         L2/L4       L4/L5        L4/L1       L4          L6           L7
```

## 時機 0：任務進來的第一秒 — L3 `/orchestrate`

### 這個工具是什麼？

`/orchestrate` 是一個「任務分類器」。在你動手之前，先把任務歸類成四種類型之一，每種類型走不同的流程。

### 四種任務類型

| 類型 | 觸發情境 | 走的流程 |
|------|---------|---------|
| `feature` | 新增功能（「加一個折扣碼」） | 需求定義 → confidence-check → 設計文件 → TDD 實作 → 文件更新 |
| `bugfix` | 修復錯誤（「購物車金額算錯」） | 重現步驟 → 根本原因 → 最小修復 → 迴歸測試 |
| `refactor` | 重構（「把這段 if-else 改得更清楚」） | 測試覆蓋率確認 → 漸進式遷移 → 效能量測 |
| `security` | 資安問題（「用戶 ID 可能被猜到」） | **唯讀調查**（不 Write）→ CVE 比對 → 隔離 worktree 修復 → 資安審查 |

### 使用方式

```
/orchestrate feature 折扣碼功能
```

### 為什麼在最開始就要做這步？

**以 security 類型為例**：如果你沒有分類就直接讓 AI 開始「修安全漏洞」，AI 可能在調查階段就開始寫修復程式碼——但資安應變的標準是「先唯讀調查，確認影響範圍，再隔離修復」。錯誤的操作順序可能讓修復不完整，或誤改到其他地方。

**分類決定工作流**，工作流決定 **每一步的限制和順序**。沒有分類就動手，等於在不知道規則的情況下玩棋盤遊戲。

## 時機 1：需求分析 — L1 幻覺偵測（7 RF + 4 Q）

### 幻覺是什麼？

AI 的「幻覺」不是 AI 說謊，而是 AI **信心滿滿地說出不正確的事實**。在需求分析階段，最危險的幻覺類型是：

| 紅旗訊號（RF） | 說明 | 範例 |
|--------------|------|------|
| RF1：過度確定 | 說「一定是」「必然」但沒有根據 | 「你的架構一定適合用微服務」 |
| RF2：假精確數字 | 給出精確數字但來源不明 | 「這套件的效能比原版快 340%」 |
| RF3：混淆相似概念 | 把類似的 API 或設計混在一起 | 把 `useState` 的用法套在 `useReducer` 上 |
| RF4：不存在的方法 | 引用一個實際上不存在的 API | `discountLib.applyCode()` — 但這個套件根本沒有 `applyCode` |
| RF5：過時資訊 | 引用舊版本的行為當作目前行為 | 「React 16 的 Context API 應該這樣用」（現在是 React 19） |
| RF6：省略限制 | 提出解法但忽略重要限制 | 建議用 Redis 快取但沒提到你的部署環境不支援 |
| RF7：假舉一反三 | 類比推理錯誤 | 「這在 Python 可行，所以在 JavaScript 也一樣」 |

### 發現 RF 後怎麼辦？用 4 個驗證提問（Q1-Q4）

| 問題 | 目的 |
|------|------|
| Q1：請提供官方文件連結 | 強迫 AI 給出可查證的 URL；AI 無法給就代表是幻覺 |
| Q2：這在哪個版本以後才支援？ | 確認版本相容性，避免引用過時 API |
| Q3：有沒有已知的限制或例外？ | 挖出 AI 省略的重要條件 |
| Q4：這個說法的信心來自哪裡？ | 讓 AI 說明依據，低信心的說法會被暴露 |

### 實際操作示範

**情境**：你請 AI 建議「如何在 Node.js 實作折扣碼驗證」，AI 回答：

> 「可以使用 `discount-validator` 套件，它提供 `validator.checkCode()` 方法，呼叫後會自動比對你的折扣碼資料庫。」

**你應該觸發 RF4 警覺**（不存在的方法名），然後問 Q1：

> 「請提供 `discount-validator` 套件的官方 npm 頁面連結。」

如果 AI 給不出來，或給出一個 404 連結，那就是幻覺確認。你需要換一個方向或自己實作。

### 為什麼在需求分析就要做幻覺偵測？

因為**幻覺在越早期被發現，成本越低**。

- 需求分析時發現幻覺 API → 成本：5 分鐘的確認時間
- 實作到一半才發現 API 不存在 → 成本：可能要重寫半天
- 上線後才發現 → 成本：線上事故處理

## 時機 2：設計規劃前的自審 — L2 `/confidence-check`

### 這個工具在做什麼？

在開始寫任何程式碼之前，`/confidence-check` 強迫 AI（和你）通過 5 道自審門檻（C1-C5）。全部通過才能進入實作。

這個 Skill 最重要的特性是 `disable-model-invocation: true`，代表 AI **不能靠自己判斷「我覺得 OK」就通過**，必須實際執行每一項檢查。

### 5 道門檻

| 項目 | 檢查什麼 | 如何執行 |
|------|---------|---------|
| C1：無重複實作 | 程式庫中有沒有已存在的類似功能？ | `grep -r "discount\|coupon" src/` 搜索相關關鍵字 |
| C2：架構合規 | 這個改動符合現有架構（MVC/分層設計等）嗎？ | 讀取 `ARCHITECTURE.md` 或現有目錄結構確認 |
| C3：有官方文件 | 要用的外部 API / 套件有可靠的文件嗎？ | 確認 npm 頁面 / 官方 docs 存在且版本對得上 |
| C4：OSS 現成品 | 有沒有開源套件已經解決這個問題？ | 搜索 GitHub / npmjs.com |
| C5：根本原因 | 清楚知道「為什麼要做這個」嗎？ | 能一句話說清楚這個功能解決什麼問題 |

### 門檻：≥ 4/5 才能進入實作

如果只有 3/5 通過，不能繼續。需要先解決 FAIL 的項目：

```
FAIL 的修復因果鏈：
C5 FAIL（不清楚根本原因）→ 先回去和需求方確認
C3 FAIL（找不到文件）→ 換方案或找備用套件
C1 FAIL（重複實作）→ 改用現有的，不重複寫
C4 FAIL（有 OSS 可用）→ 評估是否引入現成套件
```

### 初階工程師最常跳過的步驟

「但我清楚知道怎麼做，可以不用 confidence-check 嗎？」

不行。初階工程師最常犯的錯誤恰恰是**覺得自己清楚但其實不清楚**（C5 以為 PASS 但實際 FAIL）。強制自審讓你在動手前意識到「原來有一個現成套件可以用，不用自己寫」（C4 發現節省兩天工）。

## 時機 3-5：整個開發過程 — L4 七階段工作流（`/dev-workflow`）

### 這是整個流程的骨幹

七階段工作流是一個包含 7 個階段的完整開發框架，每個階段都有**前置條件**——沒有完成前一個，不能進入下一個。

### 七個階段對照表

| 階段 | 名稱 | 關鍵限制 | 目的 |
|------|------|---------|------|
| S1 | 腦力激盪 | 只輸出純文字，**禁止寫任何程式碼** | 先確定「要做什麼」，再決定「怎麼做」 |
| S2 | 建立 Worktree | `git worktree add` 建立隔離分支 | 保護 main 不被未完成的開發汙染 |
| S3 | 規劃 | 執行 /confidence-check，≥ 4/5 才繼續 | 確認動手前有足夠信心 |
| S4 | Sub-agent 探索 | 委派 Explore agent 讀檔（不是自己讀） | 保護主 Claude context 不被大量程式碼塞爆 |
| S5 | TDD 實作 | 先寫測試（紅燈）→ 再實作（綠燈） | 確保每個功能有測試保護 |
| S6 | 審查 | 執行 /review，**所有問題必須解決** | 品質閘門，不允許跳過任何問題 |
| S7 | 完成 | Commit → 移除 worktree → /session-end | 整理環境，確保主線乾淨 |

### 特別重要：S1 為什麼禁止寫程式碼？

這是初階工程師最難理解的設計。

「先想清楚再動手」聽起來是廢話，但腦力激盪階段只要讓 AI 開始「順手就寫了幾行程式碼」，就會發生以下連鎖問題：

1. 程式碼讓你覺得「已經有進展了」→ 心理上難以推翻
2. 已存在的程式碼成為限制 → 後面的決策被早期程式碼綁架
3. 需求還沒釐清就有了「已存在的實作」→ 方向一錯就要重寫

**S1 強制純文字**，就是斷開「邊想邊寫」的惡性循環。先輸出：

- 任務定義（這個功能要解決什麼問題）
- 完成標準（怎樣算是做完了）
- 不在範圍內（哪些不做）

只有文字，沒有程式碼。確認無誤後才進 S2。

### Checkpoint 安全網（Esc + Esc）

Checkpoint 是 Claude Code 的「時間機器」，讓你可以回到過去某個時間點。

**但你必須知道它的盲點**：

| 操作類型 | Checkpoint 追蹤嗎？ |
|---------|-------------------|
| Claude 用 Write 工具建立新檔案 | ✅ 追蹤 |
| Claude 用 Edit 工具修改程式碼 | ✅ 追蹤 |
| bash 中執行 `npm install` | ❌ **不追蹤** |
| bash 中執行 `rm -rf build/` | ❌ **不追蹤** |

**解法：Git Stash 雙重保護**

```bash
# 在讓 AI 執行任何 bash 磁碟操作前，先執行：
git stash push -m "before-dangerous-bash"

# AI 完成 bash 操作後，如果出問題：
git stash pop  # 還原所有改動
```

兩種保護機制的職責：

- **Checkpoint**：Claude Write/Edit 工具的操作 → 對話與程式碼
- **Git Stash**：bash 指令的磁碟操作 → npm/rm/mv 等

## 時機 3（進階版）：大型任務的並行開發 — L5 多 Agent Worktree

### 什麼情況需要多 Agent？

當任務大到一個 Claude 實例的 context 「裝不下」，或需要多個角色同時工作時。

以「大型功能重構」為例：

- 架構師需要深度思考設計決策
- 實作者需要寫大量程式碼
- 驗證者需要獨立執行測試

如果都由一個 Claude 實例做，context 會越來越長，AI 會「忘東忘西」。

### cascade-start.sh 的設計

```bash
bash cascade-start.sh my-task
```

這行指令建立 3 個獨立的 worktree（實體資料夾），每個對應一個角色：

| 角色 | 對應工作流階段 | 使用的模型 | 權限限制 |
|------|-------------|----------|---------|
| 架構師（Worker 1） | S1 腦力激盪 + S3 規劃 | Opus（最強推理） | Plan Mode（只思考，禁止 Write/Edit） |
| 實作者（Worker 2） | S4 探索 + S5 TDD 實作 | Sonnet（成本/能力平衡） | 完整讀寫 |
| 驗證者（Worker 3） | S6 審查 | Haiku（快又便宜） | 唯讀（只能讀和跑測試） |

### Branch vs Worktree：初階工程師必須理解的差異

```
新 Branch：
  git checkout -b feature/discount
  → 只是切換 git 指標
  → 所有人還是在同一個實體資料夾操作
  → 三個 Claude 同時開啟 → 互相蓋掉對方的工作

Worktree：
  git worktree add ../work-task-1 -b feature/task-1
  → 建立獨立的實體資料夾 ../work-task-1
  → 三個 Claude 各在自己的資料夾
  → 即使「同名檔案」也是不同實體路徑的副本
  → 最後 git merge 整合，不靠「小心別衝突」
```

### 成本梯度設計原則

「最貴的模型做最需要深度思考的決策，最快的模型做重複性驗證工作」

```
Opus（架構決策）：一個架構設計錯了，後面 100 行程式碼都要重寫
Sonnet（實作主力）：日常開發，成本和能力都平衡
Haiku（測試驗證）：跑測試不需要深度思考，但需要速度和成本效益
```

## 時機 6：日常維護 — L6 觀察 Hook + 自我進化

### 設置一次，持續收穫

觀察 Hook 是一個 **PostToolUse Hook**（每次工具執行後觸發），它靜默地把 AI 每次工具呼叫記錄到日誌。

```json
{"ts":"2026-06-15T08:23:41Z","tool":"Read","input":{"file_path":"src/cart.js"}}
{"ts":"2026-06-15T08:23:55Z","tool":"Bash","input":{"command":"git status"}}
{"ts":"2026-06-15T08:24:02Z","tool":"Edit","input":{"file_path":"src/cart.js"}}
```

### 三個欄位的意義

| 欄位 | 意義 |
|------|------|
| `ts` | 時間戳，知道是什麼時候的操作 |
| `tool` | 工具名稱，知道 AI 用了什麼工具 |
| `input` | 工具輸入，知道具體操作了什麼 |

### `/analyze-patterns` 的作用

累積足夠日誌後，執行：

```
/analyze-patterns
```

AI 會分析日誌，找出重複出現的操作序列，輸出「信心分數」：

```
模式：Grep → Read → Edit（出現 12 次，信心分數 85%）→ Skill 候選：code-fix
模式：git status → git add → git commit（出現 8 次，信心分數 72%）→ Skill 候選：quick-commit
```

### 信心分數門檻

```
公式：信心分數 = (出現次數 ÷ 總操作數) × 100

≥ 70%：值得建立成 Skill
40–70%：持續觀察，模式不夠穩定
< 40%：不列入候選，可能是偶發操作
```

### 為什麼這比「手動記錄最佳實踐」更好？

傳統方式：「我記得有一個好的 debug 流程，等我有空時寫下來」→ 通常永遠沒空。

觀察 Hook：不需要你記得，系統自動記錄。**你只需要繼續正常工作，系統持續學習。**

這不是「AI 變聰明了」，而是「AI 把你的隱性工作習慣自動外顯化了」。

## 時機 7：知識傳承 — L7 Plugin 封裝

### 部落知識的問題

初階工程師加入團隊時，最痛苦的事之一是：

「我的 local 跑不起來」→「你要把這個 Hook 設定一下」→「設定在哪裡？」→「問老王，他設過」→「老王今天請假」

這就是**部落知識**（tribal knowledge）：只存在資深工程師腦袋裡、從來沒被寫下來的隱性設定。

### Plugin 如何解決這個問題？

```
Plugin 目錄結構：
my-workflow-plugin/
├── .claude-plugin/
│   └── plugin.json     ← 名稱、版本、作者（Plugin 的身分證）
├── skills/
│   ├── confidence-check/SKILL.md
│   └── orchestrate/SKILL.md
└── hooks/
    └── hooks.json      ← 宣告 Hook 在哪個時機觸發
```

```bash
# 新成員安裝整套工具鏈：一行指令
bash install-skill.sh my-workflow-plugin https://github.com/team/skills personal
```

執行後，新成員的環境和老成員**完全一致**。

### `${CLAUDE_PLUGIN_ROOT}` 的關鍵設計

hooks.json 中，Hook 腳本路徑不能寫死：

```json
{
  "type": "command",
  "command": "${CLAUDE_PLUGIN_ROOT}/hooks/observe-pattern.sh"
}
```

`${CLAUDE_PLUGIN_ROOT}` 是 Claude Code 在載入 Plugin 時動態注入的路徑。不同機器上自動對應到正確位置：

```
公司機：${CLAUDE_PLUGIN_ROOT} = C:\Users\peter\.claude\plugins\my-workflow-plugin
家用機：${CLAUDE_PLUGIN_ROOT} = C:\Users\peter\.claude\plugins\my-workflow-plugin
同事機：${CLAUDE_PLUGIN_ROOT} = C:\Users\alice\.claude\plugins\my-workflow-plugin
```

這和 Python 中用 `Path.home()` 代替 `C:/Users/peter/` 是完全相同的設計哲學：**可攜性**。

### Semantic Versioning（語義版本）

Plugin 的版本號遵循 `主版本.次版本.修補版本`：

| 改了什麼 | 升哪一位 | 為什麼 |
|---------|---------|-------|
| Hook 行為改變（破壞性）| 主版本：`1.0.0 → 2.0.0` | 告訴使用者「升版前請確認影響」 |
| 新增功能但不破壞現有 | 次版本：`1.0.0 → 1.1.0` | 安全更新 |
| Bug 修復 / 文件 | 修補版本：`1.0.0 → 1.0.1` | 可以無顧慮升級 |

## 完整流水線：從接任務到知識傳承

```
┌──────────────────────────────────────────────────────────────────┐
│                     完整 7 工具防護鏈                             │
├──────────┬───────────────────────────────────────────────────────┤
│ 接任務   │ L3 /orchestrate                                        │
│          │ → 分類：feature / bugfix / refactor / security         │
│          │ → 決定接下來走哪條工作流                               │
├──────────┼───────────────────────────────────────────────────────┤
│ 需求分析 │ L1 幻覺偵測                                           │
│          │ → 7 個紅旗（RF1-RF7）掃描 AI 回覆                     │
│          │ → 4 個驗證提問（Q1-Q4）強制提供錨點                   │
├──────────┼───────────────────────────────────────────────────────┤
│ 設計規劃 │ L4 /dev-workflow → S1（禁止寫碼的腦力激盪）           │
│          │ → S2（git worktree 建立隔離環境）                      │
│          │ L2 /confidence-check → S3（≥ 4/5 才能繼續）          │
├──────────┼───────────────────────────────────────────────────────┤
│ 實作開發 │ L4 → S4（Explore agent 讀檔）+ S5（TDD：先測試）      │
│          │ L5 cascade-start.sh（大型任務：3 個並行 worktree）     │
│          │ └─ 架構師（Opus）/ 實作者（Sonnet）/ 驗證者（Haiku）  │
├──────────┼───────────────────────────────────────────────────────┤
│ 審查測試 │ L4 → S6（/review，不允許跳過任何問題）                │
│          │ L1 幻覺偵測再次檢查（測試本身也可能包含幻覺 API）      │
├──────────┼───────────────────────────────────────────────────────┤
│ 部署收尾 │ L4 → S7（Commit → 移除 worktree → /session-end）     │
│          │ Git Stash（bash 磁碟操作前）                          │
│          │ Checkpoint Esc+Esc（Claude Write/Edit 操作保護）       │
├──────────┼───────────────────────────────────────────────────────┤
│ 日常維護 │ L6 觀察 Hook（PostToolUse，全程背景記錄）             │
│ （持續） │ → /analyze-patterns（信心 ≥ 70% 的模式 → Skill 候選）│
├──────────┼───────────────────────────────────────────────────────┤
│ 知識傳承 │ L7 Plugin 封裝                                        │
│ （完成後）│ → plugin.json + hooks.json + install-skill.sh         │
│          │ → 一行指令讓新成員安裝完整工具鏈                       │
└──────────┴───────────────────────────────────────────────────────┘
```

## 初階工程師的 5 個常見誤區

### 誤區 1：「AI 說可以，所以就可以」

AI 的自信和正確性不掛鉤。使用 L1 幻覺偵測，**每一個工具建議都要驗證**。特別是 RF4（不存在的方法名），這是最難發現的幻覺類型。

### 誤區 2：「先做再說，有問題再回來改」

這對 AI 開發特別危險。AI 已經寫了 50 行程式碼後，你很難說「等等，我們重新定義需求」——因為程式碼的存在會影響後續決策。S1 強制先定義，再動手。

### 誤區 3：「Checkpoint 幫我備份了所有東西」

Checkpoint 只追蹤 Claude 的 Write/Edit 工具。bash 指令（npm install、rm、mv）完全不在 Checkpoint 範圍內。**bash 操作前記得 git stash**。

### 誤區 4：「一個 Claude 實例做所有事最方便」

當任務複雜度超過一定規模，單一實例的 context 會越來越長，AI 開始「忘記」之前說過的架構決策。L5 多 Agent Worktree 的設計，讓每個角色有乾淨的 context 專注做自己的事。

### 誤區 5：「最佳實踐以後再整理」

永遠不會「以後」。L6 觀察 Hook 從第一天就開始記錄，L7 Plugin 封裝讓「整理」變成「跑一個腳本」。把建立良好習慣的成本降到最低，才會真的去做。

## 小結：記住這一句話

> **L1 是防護眼鏡（全程戴著），L2+L3 是動工許可證（需求/設計前簽），L4 是完整施工規範（7 道閘門），L5 是工班擴編方案（大型任務），L6 是現場學習機制（行為→Skill），L7 是工法標準化（個人→團隊）。**

這 7 個工具缺任何一個，你的開發流程就有一個沒人把守的缺口。
