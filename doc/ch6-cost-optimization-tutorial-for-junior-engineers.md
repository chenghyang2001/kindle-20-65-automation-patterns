# Claude Code 成本最佳化實戰教學（Token 經濟學）

> **對象**：剛進職場的軟體工程師。
> 假設你會用 AI 寫程式、懂基本的 API 與 CLI，但還沒認真算過「AI 協作的帳單」。
> 這份教材教你把每週 $50 的 AI 開銷，**砍到剩 $5**——而且不犧牲品質。
> 所有省錢策略老師都用真實數字算過，下面的數據都是實際跑出來的。

---

## 寫在前面：一個會讓你冒冷汗的數字

想像你每週為了讓 AI 輔助寫程式，大約花 $50 美金。這很常見。但如果我告訴你——**這 $50 裡面有將近 $45，是花在讓 AI 反覆閱讀同一份專案設定檔**，而且每次都逐字重新讀過，你會不會覺得很荒謬？

但這確實是每天都在發生的事。

這份教材（出自《Claude Code in Production》第六章）不只是省錢指南，它要重新定義你的思維。傳統工程師習慣管理**記憶體**、最佳化 **CPU 時脈**——這是基本功。但當你踏入 AI 輔助開發，你管理的物件變了：

> 你現在管理的是 **Token** 和 **AI 的注意力**。

如果你還用「反正跑得動就好」的舊思維呼叫 AI，雲端帳單會讓你痛不欲生。

# 第一部分：吃錢怪獸的解剖學（錢到底花去哪了？）

## 反直覺的真相：input 才是大頭

如果你拆解每一次 API 請求的帳單，會發現一個極度反直覺的事實：

> 在一般除錯對話裡，**60%～80% 的成本來自 Input（輸入）**。
> 而 AI 真正產生的程式碼（Output）只佔 **15%～30%**。

**老師的實測**：我建模了「50 輪除錯對話」的場景，算出來——

```
總 input : 216,250 tokens → $0.6488  (81%)
總 output:  10,000 tokens → $0.1500  (19%)
```

input 佔了 **81%**。為什麼？

## 關鍵原因：API 是「無狀態」的

跟人類同事溝通是**有記憶（有狀態）**的——你昨天講過專案架構，今天說「登入頁面壞了」，同事就懂。但市面上多數大語言模型 API 本質上是 **無狀態（Stateless）** 的——**它每一秒都在失憶**。

> **迴轉壽司比喻**：你去一家很坑的迴轉壽司店。每拿一盤新壽司（AI 的 output）結帳時，老闆不只算這盤的錢，還把你**桌上之前吃過的所有空盤子全部重新算一次錢**。

那些空盤子，就是你的歷史對話、系統設定檔、剛才測試失敗的一大串 log。因為 AI 沒有記憶，每次問新問題，你的工具就得把這些全部打包重傳一次。

**具體數字**：假設你解一個 bug 來回對話 50 輪，專案裡有個 2000 字元的設定檔——這 2000 字元會被**重複傳送 50 次**。在 AI 寫出任何有用程式碼之前，你已經白白燒掉約 **10 萬 token 的純 overhead**。

## 為什麼「請給我簡短回答」沒用？

很多人為了省錢，會在提示詞最後加「請簡短回答、不要解釋」。**但這幾乎沒用**——因為你只省下了 output token，而 output 本來單價就低、佔比才 20%。那 10 萬 token 的 input 負債依然存在。

> 這就像**拿著水桶去救森林大火**。真正的省錢關鍵不在限制 AI 說話，而在於**保持你給它的背景資訊足夠精簡**。

# 第二部分：保護快取（最大的省錢機制）

## Prompt Caching：把重傳的成本打 1 折

既然 input 是最大破口，那些每次重傳的「空盤子」怎麼辦？答案是 **Prompt Caching（提示快取）**。

> 只要你的上下文沒變動，後續每次請求的輸入成本，大約只需要原本的 **10%**（打 1 折）。原本 10 萬 token 的成本，瞬間降到 1 萬多。

**老師的實測**：固定設定檔在 50 輪中——無快取 $0.0750，有快取 $0.0090，**省 88%**。

## 但快取極度脆弱：exact prefix matching

快取的底層邏輯是 **前綴精確比對（exact prefix matching）**，TTL 約 5 分鐘。當新請求進來，伺服器從頭一個 token 一個 token 比對——**只要有一個字元不一樣，後面全毀**。

**真實踩坑**：有人為了除錯方便，寫了個腳本在提示詞**最上面**自動印出當前系統時間。結果他親手毀掉了所有快取折扣——因為每秒時間都不同，伺服器比對第一個 token 就 mismatch，判定 **cache miss**，後面幾萬 token 全部按原價重算。

**老師的實測**（模擬前綴比對）：

```
[好設計] 穩定 CLAUDE.md 放開頭：共同前綴 803 字元 → 99% 命中快取
[壞設計] 跳動時間戳放開頭：    共同前綴 19 字元  → 快取命中 0%
```

## 解法：地基層思維

範例 `docs/cache-design-guide.md` 給出 CLAUDE.md 的設計原則：

| 放哪裡 | 放什麼 | 為什麼 |
|--------|--------|--------|
| **最上面（穩定區）** | 專案架構、技術棧、命名慣例、基礎工具定義 | 像基岩一樣不動，永遠命中快取 |
| **最下面（變動區）** | 當前工作狀態、最近改動、TODO | 每次變，放底部才不會破壞上面的快取 |

> 把最穩定的東西像地基一樣放最底層，伺服器比對時確認「前面 90% 沒變」，直接套 1 折，只對最後新增的內容全額計費。

# 第三部分：戰略性壓縮（對抗上下文膨脹）

快取解決了靜態設定檔，但**對話記錄本身會越來越長**。解到 30、40 輪時，那個包裹還是會膨脹得很可怕。這時要用 `/compact` 手動壓縮。

## 質疑：壓縮不就讓 AI 失憶了嗎？

好問題。假設你正解一個難 bug，前面試過三種失敗解法，現在壓縮了——它會不會忘記失敗經驗，又跑去試第一種錯誤解法，反而更浪費？

**所以壓縮必須是「戰略性」的**——重點不在盲目看 token 變多就壓，而在**時機**和**內容**。

## 對的時機：任務斷點（存檔點）

系統預設的自動壓縮太保守，會等到快頂到極限才啟動——但那時已經付了太多過路費。正確做法是在**任務斷點手動介入**。

> **遊戲存檔點比喻**：你剛解完一個記憶體洩漏 bug、PR 也合併了。打完王之後，你要記住的是「我打贏了、拿到鑰匙、現在滿血」，而不是「打王過程中每一次的閃躲」。

在斷點手動壓縮，把過程濃縮成：

```
已修復 UI cast 的記憶體洩漏問題，PR 已合併，
系統處於穩定狀態，準備進行下一個 UI 渲染任務。
```

保留關鍵的全域狀態，清空幾萬個已失去價值的除錯過程。對於鬼打牆的除錯，還可用 **「summarize from here」**——保留最初完美的架構討論，只抹掉中間「嘗試→爆錯→再嘗試」的泥沼。

## 怎麼知道何時該存檔？盯著 token 計數器

> 「你無法最佳化你無法衡量的東西。」當計數器到 **50%～70%**，就是該找下一個存檔點的訊號。

**範例 `hooks/suggest-compact.sh`** 自動幫你盯——每累積 50 次工具呼叫就提醒。**老師的實測**：

```
49 次工具呼叫 → 無提醒
50 次工具呼叫 → "Consider running /compact (tool calls: 50)"
100 次       → 再次提醒
```

# 第四部分：模型選擇與子代理套利

## 不要無腦選最強的 Opus

很多人有不安全感，覺得「既然用 AI 就選最強的 Opus 最保險」。但攤開定價表——**最輕的 Haiku 和最強的 Opus 差距高達約 20 倍**。

**老師的實測**：Haiku input $0.80/M ←→ Opus input $15/M = **19 倍**。跑一次 Opus 的錢，可以讓 Haiku 跑 19 次。

## 核心原則：按「認知需求」匹配，不是按任務類別

範例 `model-selection-matrix.md`：

| 任務 | 模型 | 理由 |
|------|------|------|
| 程式碼搜尋、檔案探索、格式化 | **Haiku** | 只需閱讀速度 + 基礎模式辨識，不需深度推理 |
| 寫新功能、重構、安全審查 | **Sonnet** | 性價比最高的主力軍 |
| 系統底層架構、極模糊需求 | **Opus** | 鎖在保險箱，只在必要時請出來 |

## 子代理套利：本章最高階的技巧

痛點：我在主對話用昂貴的 Sonnet，遇到一個「去 40 個檔案找某函式」的瑣事，難道要切換成 Haiku 再切回來？太麻煩。

**解法**：直接在主對話建立一個**強制用 Haiku 的子代理**（範例 `agents/code-explorer.md`），叫它當「程式碼庫探險家」。關鍵在它的底層機制：

> 這個 Haiku 子代理在**後台開一個完全獨立、被隔離的 context**。它在自己的小房間讀了 40 個檔案、消耗 5 萬 token，找到答案後**只回傳一份 400 字的精華摘要**給昂貴的主對話。那個裝著 5 萬 token 的小房間，任務結束瞬間直接丟棄——用過即丟。

**老師的實測**：

```
方案A 直接灌進 Sonnet 主對話：5萬 token × Sonnet → $0.1500
方案B Haiku 子代理讀+回400字：5萬×Haiku + 400×Sonnet → $0.0412
→ 省 73%
```

你利用了**廉價模型的搜尋廣度**，保護了**昂貴主對話的上下文純淨度**。字稿形容這像「高頻交易的金融套利」。

# 第五部分：MCP 的隱形吃錢怪獸

## 掛一個 MCP 工具，不只是給個 URL

你可能以為掛 MCP 工具只是給 AI 一個 API 介面。但抓包看底層傳輸會發現——當你啟用一個 MCP server，系統必須把**工具的完整說明書**（有哪些功能、每個參數的型別、哪些必填）轉成一個龐大的 **JSON schema**，**強制注入你每一次的 API 請求**。

> **範例**：為了 E2E 測試掛載 Playwright MCP，它含 23 個小工具。不管你這輪只是在微調一個 CSS 顏色，這 23 個工具、幾千 token 的 JSON 說明書，都默默跟著每次請求一起傳、一起計費。
>
> 就像你去山腳野餐，卻全程背著攀聖母峰的全套雪地裝備、冰斧、氧氣桶。

## 解法：Wrapping in Skills（用自然語言包裝）

與其讓 AI 直接面對龐大的 JSON 工具定義，不如建立一個 bash 腳本，再用**一段簡短的自然語言**告訴 AI 怎麼呼叫它。為什麼省 token？因為 **AI 本來就是為理解自然語言而生的**——你不需要給它幾千 token 的嚴格 JSON 結構。

範例 `skills/take-screenshot/SKILL.md` 就是這樣，短短幾句話包住 playwright 指令。

**老師的實測**：

```
Skill 版（take-screenshot SKILL.md，自然語言）: ~87 token
MCP 版（Playwright 23 工具 JSON schema）     : ~4,600 token
→ 100 輪開發對話累積省下 451,300 token（字稿說約 30 萬，量級吻合）
```

> 我們把複雜的工具邏輯藏在腳本背後，AI 只需要知道「有這個按鈕可以按」，完全不需要知道按鈕背後的電路板怎麼接。

## 但不是所有 MCP 都該換（`mcp-to-skill/README.md`）

| 保留 MCP | 改用 Skill |
|----------|-----------|
| 需要跨呼叫維持狀態 | 單一 CLI 指令 |
| 需要 OAuth/複雜認證 | 抓公開文件 |
| 需要串流大量資料 | 簡單文字處理 |

# 第六部分：成本護欄（硬性財務紀律）

## 終極防護網：關掉 1M context

現在的模型動輒支援 1M（100 萬）token 的超大上下文。聽起來很棒——你可以把整個 GitHub repo 塞進去。但對你的信用卡來說，這是個**無底洞**：

> 當對話累積越過約 **200k（20 萬）token**，很多 API 的計費會**跳轉到更貴的費率級**。

範例 `settings/disable-1m-context.json` 設定 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`。這不是閹割能力，而是 **Cost Guardrail（成本護欄）**——強迫你拔掉無底洞選項。當對話快碰到標準視窗上限，系統強迫你停下來，回頭用 `/compact` 壓縮。這是一種**硬性的財務紀律**，在系統層面強制你養成好習慣。

其他護欄設定：

- `settings/minimal-mcp.json`：deny 掉吃 token 的重型 MCP（playwright/magic）
- `cost-monitoring.md`：用 `--output-format json | jq '.usage'` 隨時量測（無法衡量就無法最佳化）

# 結語：Token 經濟學複雜度

把這幾招組合起來，真的是從 $50 降到 $5 的魔法：

| 策略 | 省下什麼 |
|------|---------|
| 看懂帳單（input 佔大頭）| 不再花冤枉錢限制 output |
| 保護快取（地基層思維）| 重傳成本打 1 折（省 88%）|
| 戰略性壓縮 | 清掉失去價值的除錯過程 |
| 子代理套利 | 廉價模型做苦工（省 73%）|
| MCP 包成 Skill | 100 輪省 45 萬 token |
| 成本護欄 | 防無底洞跳貴費率 |

## 一個全新的複雜度概念 🤔

傳統軟體工程用 **Big O 符號** 評估演算法的時間與空間複雜度。隨著 AI 代理普及，我們或許正在見證一種全新的複雜度誕生：

> **Token 經濟學複雜度（Token Economics Complexity）**
>
> 未來的頂尖工程師，比拼的或許不再是誰寫的迴圈跑得快，
> 而是**誰能最優雅、最精簡地編排 AI 的認知預算**——
> 如何在最低的 token 消耗下，引導 AI 產出最高品質的系統架構。

這不再只是省幾塊錢的問題，而是展現你對這套全新運算架構的**控制力**。

下次當你在終端機準備按下 Enter 呼叫 AI 時，讓手指停在半空中三秒，想一想：

> 你現在打包送出去的這個包裹裡，裝的是**真正引導 AI 解決問題的關鍵線索**，
> 還是**一堆昂貴又無效的空盤子**？

現在，就去檢查一下你的快取設定吧。
