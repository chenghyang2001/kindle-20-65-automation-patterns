# Claude Code 權限與安全實戰教學（三層防禦架構）

> **對象**：剛進職場的軟體工程師。
> 假設你會用 AI 寫程式、懂基本的檔案權限與 CLI，但還沒設計過「組織級的 AI 安全防護」。
> 這份教材教你建立一套三層防禦網，**不只防外面的駭客，更是保護你自己免受自己的傷害**。
> 所有範例老師都實際跑過——其中一個範例的防線，還在 demo 過程中親身攔截了老師。

---

## 寫在前面：凌晨三點按下核准鍵的那一刻

想像一個極度寫實的畫面：

> 凌晨三點，你盯著螢幕，旁邊一杯早就冷掉的咖啡。為了趕早上八點的釋出，你已奮戰十幾個小時，大腦幾乎無法思考。這時 AI 助理彈出提示框，問你要不要執行一串超長、充滿奇怪符號的 bash 指令。你太累了，心想「反正它剛才幫我修好三個 bug，這次應該也不會錯」——滑鼠一點，按下核准。
>
> 下一秒，一連串不可逆的資料庫重置指令，在你的正式環境裡爆發了。

這點出一個殘酷的真相：當我們把高度自主的 AI 代理放進開發流程，**最致命的資安破口往往不是外部駭客，而是內部一個疲憊、為了趕時間而盲目授權的工程師**。

所以本章的核心精神是：

> **建立安全網，不只為了防外面的壞人，更是為了保護你免受自己的傷害。信任不能取代控制。**

我們要建構一套**三層防禦架構**。光靠道德勸說或幾條開發規範絕對不夠。

---

# 三層防禦總覽

| 層級 | 是什麼 | 實習生比喻 |
|------|--------|-----------|
| **第一層：權限模型** | 定義 AI 絕對不能碰的紅線 | 第一天遞給它的員工手冊（哪些抽屜能開、哪些資料夾不能碰）|
| **第二層：管理設定** | 組織由上而下強制介入的鐵腕政策 | 把機房和財務部的門換成只有主管門禁卡能刷的電子鎖 |
| **第三層：沙盒機制** | 作業系統底層的物理限制 | 把所有危險化學物品搬到另一棟建築（就算闖進禁區也生不出亂子）|

關鍵洞察：**員工手冊的規則會被曲解或繞過**（規矩是死的），**人類會因疲勞犯錯，AI 會被複雜上下文誤導**——所以不能只停在第一層。

---

# 第一部分：第一層——權限模型（員工手冊）

## Deny > Ask > Allow 的死板優先序

系統評估規則遵循一個非常死板的順序（範例 `permissions/layered-permissions.json`）：

```json
{
  "permissions": {
    "deny":  ["Bash(git push *)", "Bash(rm -rf *)", "Read(./.env)"],
    "ask":   ["Bash(git commit *)", "Bash(docker run *)"],
    "allow": ["Bash(npm run test *)", "Read(src/**)", "Edit(src/**)"]
  }
}
```

**只要系統讀到一條 Deny，後面的設定連看都不看**——這是絕對否決權。

## 為什麼 Deny 必須「不可談判」？

因為像 Claude 這樣的 LLM 本質上非常擅長文字推理和講道理。處理複雜除錯時，它可能構造出極有說服力的理由：

> 「為了確認資料庫連線字串是否正確，我必須讀取環境變數檔案 .env。」

聽起來很合理對吧？但當你凌晨三點腦袋疲弱時，**很容易就被說服按下核准**。有了底層 Deny 規則，AI 的讀取工具在發動瞬間就被攔截——**它連開口問你的機會都沒有**。短程的不方便，換來系統永遠不會因一個失誤而把正式環境機密外洩。

## 一個空格的生死差異（本章最驚人的細節）

設定允許哪些 bash 指令時，看這兩個寫法：

```
Bash(ls *)    ← ls 和星號之間「有」空格
Bash(ls*)     ← ls 和星號之間「沒」空格
```

唯一差別就是一個空白鍵。但**這個空格是資安生與死的關鍵**：

| 寫法 | 系統如何理解 |
|------|-------------|
| `Bash(ls *)` 有空格 | 「ls 這個**指令** + 後面接任意參數」（空格形成**單字邊界**）|
| `Bash(ls*)` 無空格 | 「任何**以 ls 開頭**的指令」（前綴比對）|

**老師的實跑驗證**（模擬 Claude Code 的 pattern 比對）：

```
指令          | Bash(ls *) 有空格 | Bash(ls*) 無空格
------------- | ----------------- | -----------------
ls -la        | ✅放行            | ✅放行
lsof -i :22   | 🚫擋下            | ✅放行  ← 危險！
```

`lsof`（List Open Files）能列出系統所有開啟的檔案和網路埠，是駭客做 **port scanning（埠掃描）** 探測漏洞的工具。一個工程師原本只是好意設了萬用字元方便 AI 列檔案，**只因少敲一下空白鍵，就在無意間幫惡意網路掃描工具敞開了大門**。

> 這說明了：防禦不能只靠第一層——因為人類在寫規則時本身就很容易留破綻。

# 第二部分：第二層——管理設定（鐵腕政策）

## 防止「老鳥偷改設定」

第一層有個現實漏洞：一個覺得設定很麻煩的資深工程師，可能想「規矩是死的，人是活的」，在自己本地專案資料夾偷偷加一條 `allow: 所有 bash 指令`——公司的第一層防禦就瞬間形同虛設。

解法是**層級覆蓋**。權限優先序由上而下：

```
組織管理層設定（最高）> 命令列引數 > 本地專案設定 > 個人設定（最低）
```

放在系統最頂端的 **Managed Settings** 就像擁有絕對否決權的上方保鑣（範例 `managed-settings/managed-settings.json`）：

```json
{
  "permissions": { "deny": ["Bash(git push --force *)", "Read(~/.*)"] },
  "disableBypassPermissionsMode": "disable",
  "allowManagedPermissionRulesOnly": true
}
```

只要資安團隊在最高層級啟動 `allowManagedPermissionRulesOnly`，**工程師在自己電腦偷加的放寬規則，系統執行時直接無視**。開發者再也無法私自開後門繞過公司限制。

（macOS 上對應的是系統級的 `com.anthropic.claudecode.plist`，由 IT 統一派發。）

## 妙用：看緊老闆的錢包

這招還能控制成本。AI 代理執行時常啟動自動化思考迴圈——如果它因某個複雜錯誤陷入無限迴圈，可能一分鐘內發出上百次 API 請求。如果用的是最貴的頂級模型，**你去泡杯咖啡的時間，幾萬塊台幣就憑空燒掉了**。

透過管理設定強制只能用輕量、低成本的模型，從根本上把「吃錢怪獸」從選項裡移除。

## plan mode：只能看不能摸的博物館導覽員

code review 時，可以強制把 AI 設為唯讀的 plan mode（範例 `permissions/readonly-review.json`）：

```json
{
  "defaultMode": "dontAsk",
  "deny": ["Bash", "Edit", "Write", "WebFetch", "mcp__*"],
  "allow": ["Read(./src/**)", "Grep", "Glob"]
}
```

這姿態下 AI 依然能掃描幾千行程式碼找漏洞、寫嚴密的審查報告——但**底層被剝奪任何修改能力，連試一下都不行**。這呼應企業資安最高指導原則：**最小權限原則**。搭配底層寫死的 Deny 規則，等於雙重保險。

# 第三部分：攔截器 Hooks（X 光安檢機）

前兩層都在防「AI 去做我們不允許的事」。但有時最可怕的炸彈藏在**我們允許的操作**裡。這就需要攔截器（PreToolUse hook）。

## 最致命的例子：機密外洩

AI 處理專案時可能**合法地**讀到臨時 API Key 或登入 Token。讀取是合法的——但它有時在寫日誌或系統報告時，會不小心把這些機密當成普通字串寫出來。如果這時 AI 正在 `git commit` 推送到遠端——**這個機密就會被永遠刻進版本控制歷史**。如果是開源專案，等於全世界都看得到你家資料庫密碼。

## 解法：寫入前先過 X 光

範例 `hooks/secret-scanner.sh` 是個 PreToolUse 攔截器。每當 AI 準備 Write/Edit，它用預寫的正規表示式掃描即將輸出的內容，比對 7 種 secret 格式（AWS / GitHub / Anthropic / OpenAI / Google / Stripe / 私鑰）：

```bash
PATTERNS=( "AKIA[0-9A-Z]{16}"  "gh[ps]_[A-Za-z0-9]{36}"  ... )
for i in "${!NAMES[@]}"; do
  if echo "$CONTENT" | grep -qE "${PATTERNS[$i]}"; then
    echo "{\"decision\":\"block\",\"reason\":\"Secret detected: ${NAMES[$i]}\"}" >&2
    exit 2     # 攔截！
  fi
done
```

> **機場安檢比喻**：就算你有合法的登機證（寫入檔案的權限），如果 X 光掃到行李裡藏著違禁品（不小心帶出的 API Key），你依然過不了這道門。

## 老師的真實實跑（含一個 meta 時刻）

老師建了含假 AWS key / GitHub token 的測試輸入，餵給範例 secret-scanner.sh：

```
測試1：寫入含 AWS key → {"decision":"block","reason":"Secret detected: AWS"} → exit 2 ✅
測試2：Edit 含 GitHub token → {"decision":"block","reason":"Secret detected: GITHUB"} → exit 2 ✅
測試3：寫入乾淨內容 → exit 0 放行 ✅
```

**最有趣的是**：老師的開發環境**本身就部署了這個 secret-scanner**（`~/.claude/hooks/`）。當老師寫含 AWS key 的測試檔時，老師自己環境的這道防線**當場攔截了老師**，回報 `Secret detected: AWS`。這證明範例不是紙上談兵——它是真實在用、真實有效的防線。

## 為什麼必須在工具呼叫「之前」掃描？

這是為了合規性。對需要 SOC 2 這類最高級資安認證的組織，系統日誌的安全性是重中之重。

> 如果機密資訊已被寫進日誌檔，**就算指令最後沒執行成功，在合規標準裡依然是一次嚴重的資安違規（Data Breach）**。

攔截器在指令發動前就介入，這些機密字串根本連進入日誌的機會都沒有。

## 攔截器還會「對話」

攔截不只是擋下來。它回傳 `exit 2` + 一段錯誤訊息告訴 AI：「我發現了潛在機密，請移除後再試。」這建立了一個**反饋迴圈**，讓 AI 知道自己錯在哪並自我修正——賦予系統自我修正的韌性。

## 另一種攔截：防止 CI 流水線卡死

範例 `hooks/dev-server-blocker.sh` 展示另一種攔截。`npm run dev` 這類開發伺服器**設計上就是要一直執行、等待連線，永不自己結束**。在你的終端機按 Ctrl+C 就能關掉，但在**無人值守的 CI 流水線**裡，整條流水線會永遠卡死（hanging）直到 timeout 當機。

攔截器的聰明處：它檢查 `TMUX` 環境變數——

```bash
if [[ -z "$TMUX" ]]; then   # 不在 tmux = 自動化環境 → 攔截
  echo "{\"decision\":\"block\",...}" >&2; exit 2
fi
```

**老師的實跑**：

```
npm run dev（無 TMUX，自動化環境）→ 🚫 block exit 2
npm run build（一般指令）          → ✅ 放行
npm run dev（模擬 tmux 互動環境）  → ✅ 放行（人類在用，沒問題）
```

它能區分「人類在 tmux 互動」（放行）和「無人值守 CI」（攔截）——默默守護系統運作的無名英雄。

# 第四部分：第三層——作業系統沙盒（絕對武力）

前面都很完美。但如果 AI 遇到的不是自己犯傻，而是**極度狡猾的外部敵人**呢？

## 最棘手的難題：Prompt Injection（提示詞注入）

想像一個極端場景：你的 AI 正在分析一個開源套件，讀取它的 README——但這個 README 早被惡意攻擊者篡改，裡面藏了一段精心偽裝的指令，用文字騙 AI 構造出一個極具破壞力的系統刪除指令。

問題在於：**AI 被文字邏輯騙了，它認為自己在執行一項合法任務**。這個由惡意內容借 AI 之手組合出的指令，可能完美避開 Deny 規則、也不含任何需要被攔截的機密——**在第一層和第二層防禦眼中，這完全是合法操作**。機遇規則和內容掃描的防禦全面失效。

## 動用絕對武力：OS 核心層沙盒

這時只能動用資安領域的絕對武力——第三層的**作業系統層級沙盒**（macOS 叫 **Seatbelt**，Linux 叫 **Bubblewrap**）：

```json
{ "sandbox": { "network": { "allowedDomains": ["registry.npmjs.org","api.github.com"] } } }
```

> 沙盒**根本不管你的指令長什麼樣、不在乎 AI 覺不覺得合法**——它在作業系統核心層級攔截。我們用設定檔把 AI 啟動的程式關進極度受限的環境：只能在特定工作目錄寫檔；要連網的話，所有流量強制透過受控代理（範例 `proxy-config.json`），只能連白名單網域。

這等於把 AI 關進一個**透明的防爆玻璃箱**，只開幾個小孔讓它拿到我們允許的工具。就算 AI 因 prompt injection 中毒發瘋，試圖刪系統核心檔案或把資料傳到駭客伺服器，**它能破壞的範圍絕對跨不出玻璃箱半步**。

## 沙盒限制會「遺傳」

更強大的是：當 AI 下一個 bash 指令，這個指令可能衍生出其他子進程（呼叫 curl 下載、啟動 pip 安裝）。在作業系統層級，**這些 AI 衍生的所有子進程，通通自動繼承那個防爆玻璃箱的嚴格限制**——惡意程式無處可逃。

這對受高度監管的產業（醫療 HIPAA、金融 PCI DSS）至關重要：有沒有這層沙盒，是「AI 操作也許符合資安政策」與「AI 在系統物理結構上根本無力違規」的決定性差異。

> 前者我們還在賭機率、靠信任；後者，我們靠的是堅不可摧的系統物理限制。

---

# 結語：信任不能取代控制

我們從第一層的權限規則出發（不可談判的 Deny、一個空白鍵的網路掃描危機），進入第二層的管理設定強制介入與 plan mode 唯讀，安裝了 X 光攔截器在機密寫入日誌前就擋下，最後啟動終極的 OS 沙盒，用核心層級的物理限制粉碎 prompt injection 的威脅。

| 防線 | 能被繞過嗎？ |
|------|------------|
| 第一層 權限規則 | 可能被曲解、被本地偷改 |
| 第二層 管理設定 | 由上而下強制，本地改不動 |
| 第三層 OS 沙盒 | **物理上無法違規** |

最大的思維翻轉是：

> 在 AI 能力指數級爆發的時代，導入 AI 開發工具**絕對不能建立在「對 AI 聰明才智的信任」上**。我們必須像嚴謹的建築師，為它打造多層次的護欄。

有了這三層防禦，開頭那個凌晨三點按下核准鍵的工程師，終於可以安心去睡個好覺了。

## 留給你的思想實驗 🤔

談了這麼多防禦與限制，這引出一個更深的矛盾：

> 隨著未來 AI 越來越強大，甚至能完全自主規劃架構、自我除錯修復系統時——
> 我們人類的資安防禦思維，究竟是會繼續沿今天的邏輯，撰寫成千上萬條更複雜細微的微觀管理規則？
> 還是走向另一個極端：徹底放棄繁瑣的設定檔，**完全依賴物理級別的絕對沙盒**，在這個堅固的防爆箱裡，放手讓 AI 擁有 100% 的自由去發揮？

在這個 AI 迭代速度超越想像的時代，人類與 AI 之間那條信任的邊界，究竟該畫在哪裡？
