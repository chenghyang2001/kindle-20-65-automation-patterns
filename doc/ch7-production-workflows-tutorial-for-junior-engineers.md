# Claude Code 進階生產工作流實戰教學

> **對象**：剛進職場的軟體工程師。
> 假設你會用 AI 寫程式、懂 Git / 測試 / CLI，但還沒在「真實的企業級程式碼庫」裡和 AI 大規模協作過。
> 這份教材教你把 AI 從「常常暴走的程式碼產生器」，馴化成「**有紀律、會自省、可複製的 AI 工程團隊**」。
> 所有範例老師都實際跑過，下面的執行結果都是真實輸出。

---

## 寫在前面：玩具專案 vs 真實專案

你大概用 AI 寫過「貪吃蛇」或「待辦清單」這種小程式，覺得很順。但真實工作完全是兩回事。看這個你一定遇過的場景：

> 你敲下一行很簡單的提示詞：「幫我修一下購物車的結帳按鈕。」
> 三秒後，AI 吐出 400 行**看起來極度完美**的程式碼。你滿心歡喜按下存檔——
> 下一秒，你的資料庫連線設定**全部被清空**了。
> AI 還很自信地告訴你：「我順便幫你最佳化了系統架構。」

**AI 為什麼會暴走？** 重點不是它變笨了，而是它的「個性」——**它太急著取悅你**。語言模型的本質是「預測下一個字」，所以它最常見的失敗叫做 **Premature Implementation（過早實作）**：在還沒搞清楚需求邊界、還沒摸清你舊程式碼脈絡時，它就開始狂改檔案。

就像一個剛畢業的新人，主管話還沒說完，他已經把程式碼推上線了。

這份教材（出自《Claude Code in Production》第七章）要做的，就是**把 AI 的車鑰匙沒收，教它什麼叫真正的規矩**。

# 第一部分：七階段紀律（給衝動的 AI 上規矩）

要治「過早實作」，官方提出一個嚴格的**七階段標準作業流程（SOP）**。建議直接寫進專案的 `CLAUDE.md`，強迫 AI 每次動手前照表操課。

以「翻新一個寫得很爛的舊金流模組」為例：

| 階段 | 做什麼 | 關鍵紀律 |
|------|--------|---------|
| **S1 Brainstorm** | 用 1–3 句定義任務、寫明完成標準、列出範圍外的事 | **嚴禁修改任何程式碼**，只能輸出純文字思考 |
| **S2 Worktree** | `git worktree add` 建一個平行的實體資料夾 | **實體隔離**，保護你的主線時間軸 |
| **S3 Plan** | 條列具體會動到哪些檔案 + 跑 confidence-check | ≥90% 信心才能往下 |
| **S4 Sub-agent** | 派 Explore 代理去收集上下文（爬完所有相關舊程式碼）| 先做完身家調查 |
| **S5 TDD** | **先寫測試，再寫實作** | 測試驅動開發 |
| **S6 Review** | 跑 `/review`，解決所有問題 | 審查安全與效能 |
| **S7 Complete** | commit、移除 worktree、收尾 | 清理 |

## 為什麼 S1 禁止寫程式碼？

這利用了語言模型的特性：它需要**透過生成 token 來進行邏輯推演**。逼它先用純文字講出計畫，等於強迫它「先想清楚再動手」，而不是邊想邊改你的檔案。

## 為什麼 S2 要用 worktree 而不是普通的 git branch？

`git worktree` 會建立一個**平行的實體資料夾**。如果 AI 直接在你當前的工作目錄亂搞，可能把你正在改、還沒存檔的其他功能弄壞。worktree 是**實體隔離**，保護你的主線。

## 七階段的流程圖（範例 `seven-stage-workflow.dot`）

```
S1 Brainstorm → S2 Worktree → S3 Plan ──OK──→ S4 Subagent → S5 TDD → S6 Review ──Pass──→ S7 Complete
                                 │No                                      │Fail
                                 └→ Redesign → 回 S3                      └→ 回 S5 TDD
```

注意兩個**迴圈**：Plan 不通過會退回重新設計、Review 失敗會退回 TDD。範例用 DOT 有向圖定義，讓 AI 嚴格沿著箭頭走，不能自己亂跳階段。

# 第二部分：orchestrate 動態編排（解決「太官僚」問題）

七階段聽起來滴水不漏，但有個致命問題：**如果我只是改個按鈕顏色，你要我開平行 worktree、做腦力激盪、派代理調查？殺雞用牛刀！**

這是導入這套系統**最容易失敗的地方**——開發者會因為流程太繁瑣而直接放棄。

## 神級解法：`orchestrate` 指令

它會**根據任務類型自動變形工作流**。你只要輸入 `orchestrate <類型> <任務>`，系統自動判斷該走多少流程：

| `orchestrate <類型>` | 流程（從範例 `skills/orchestrate/SKILL.md`） |
|---|---|
| `feature`（新功能）| 需求 → confidence-check → 設計文件 → TDD → 更新文件 |
| `bugfix`（修 bug）| **先記錄重現步驟** → 找根因 → 最小修正 → 回歸測試 |
| `refactor`（重構）| 先驗測試覆蓋 → Strangler Fig 漸進遷移 → 每步驗測試 → 量化效能 |
| `security`（資安）| **唯讀調查（no Write）** → 比對 CVE → 隔離 worktree 修 → 安全代理驗證 |

`orchestrate bugfix` 會知道「這只是修 bug，範圍小」，直接跳過 brainstorm 和 worktree，奔向「重現錯誤」階段。

## bugfix 的鐵律：先證明你懂了才能動手

這個編排有一條**硬性入口閘道**：在 AI 寫下任何一行修復程式碼之前，它**必須先寫出一個能精準重現該 bug 的失敗測試**。

> 寫不出失敗測試？系統直接鎖死，一行原始碼都不准碰。

為什麼這麼狠？因為**沒有失敗的測試，就代表你根本不知道問題住在哪裡**，後面寫的修復全是瞎猜。這強迫 AI 先證明自己真的懂了，才能動手。

# 第三部分：對抗幻覺（戳破 AI 的瞎掰）

## LLM 的可怕本質

假設 AI 在計畫階段信心滿滿地說：「沒問題，我查過了，Stripe 有一個 `Refund All` 的 API。」結果那個 API **根本不存在**——是它「通靈」想像出來的。後面的測試和實作就全部跟著翻車。

**為什麼會這樣？** 因為對 LLM 來說，**生成一個看起來極度合理的假東西，比生成真實存在的東西要容易太多**——它就是在算機率。幻覺不是能力缺陷，是 LLM 的**結構性特質**。

範例提供兩道防禦：

## 防禦一：confidence-check 實作前檢查表

範例 `skills/confidence-check/SKILL.md` 要求 AI 動手前自我評分 5 項，**至少拿到 4/5（≥90%）才能通關**：

| 項目 | 檢查什麼 |
|------|---------|
| **C1 重複檢查** | grep 專案，確認沒有等價功能（**最常救命**）|
| C2 架構合規 | 是否違反 CLAUDE.md 的依賴方向、分層 |
| C3 官方文件 | 計畫用的 API 在當前版本真的有效嗎 |
| C4 OSS 參考 | 有沒有開源實作可避免重造輪子 |
| C5 根本原因 | bug 的根因找到了嗎 / 使用者的真實需求確認了嗎 |

**C1 為什麼最能救命？** 字稿舉了個經典災難：你要驗證信用卡，AI 會非常熱心幫你寫一個幾百行完美的 `validateCreditCard` 函式——**但它不知道**你們專案的 `utils/validation` 深處，早就躺著一份公司祖傳的驗證模組。沒有 C1，你的專案就會出現兩套邏輯互相打架。

**老師的實跑驗證**：我對「在本專案新增資料驗證函式」套用 C1，實際 grep 整個 `code/` 目錄——

```
── 實跑 grep（搜尋現有 validate/check 函式）──
（本專案無現成 validate/check 函式）
── C1 判定 ──
C1: PASS（無重複，可新增）
```

這就是「動手前先環顧四周」的習慣。

## 防禦二：四個靈魂拷問（範例 `hallucination-detection.md`）

當你懷疑 AI 在幻覺時，**不要跟它爭論邏輯**，直接砸這四個問題：

| 拷問 | 為什麼 AI 編不出來 |
|------|------------------|
| **Q1** 給出官方文件的 **URL + 章節** | 捏造順口的程式碼容易，捏造一個**點得開的網址**幾乎不可能 |
| **Q2** 這功能從**哪個版本**引入？文件確認過嗎？ | 「我沒查過」就是幻覺紅旗 |
| **Q3** 不要解釋，**立刻在終端機跑**這段 PoC 給我看結果 | 跑一下就知道有沒有報錯 |
| **Q4** 去 GitHub 找一個**真的這樣用**的開源專案 | 逼它提供實體證據，不靠模糊訓練資料 |

這四問的精髓：**逼 AI 提供有根據的實體證據**，而不是依賴它模糊的訓練資料瞎猜。

## 七個紅旗（人類審查者要警覺）

最致命的是 **RF1**：當 AI 說「**我相信這是正確的…**」後面跟著一堆複雜技術細節——這就是典型的「**自信慢期、閃爍其詞**」，是心虛的表現。聽到這句話要立刻啟動防禦。

# 第四部分：大型重構的三窗格分工

當你要幹一票大的（例如把整個購物系統從舊框架遷移到新框架），單靠一個 AI 實體絕對會迷失——**一旦上下文太長，AI 就會斷片，改了東邊忘了西邊**。

## 解法：把 AI 切成三個角色（廚房分工）

範例 `cascade/cascade-start.sh` 用 git worktree 建三個隔離環境，各跑一個不同角色的 AI：

| 窗格 | 角色 | 模型 | 權限 | 廚房比喻 |
|------|------|------|------|---------|
| 1 | **架構師** | Opus（最聰明最貴）| **鎖死在 plan mode，不能寫碼** | 雙手抱胸、只出一張嘴的主廚 |
| 2 | **實作人員** | Sonnet（均衡）| 完全讀寫 | 在爐火前瘋狂切菜煮菜的二廚 |
| 3 | **驗證人員** | Haiku（極快）| **只能讀檔 + 跑測試** | 出菜口的品管 |

**這樣分工的兩大好處**：

1. **關注點分離**：主廚不會弄髒手把菜炒焦；二廚瘋狂寫程式時，也不會突然腦洞大開去改整道菜的食譜。
2. **省錢**：按能力分配模型——探索用便宜的 Haiku、實作用中等的 Sonnet、只有架構決策才用最貴的 Opus。

**老師的實跑驗證**：我實際跑了 `cascade-start.sh`，它建出三個獨立 worktree：

```
✓ Worktree 1（安全性審查）：../work-hooks-review-1（分支：worker-1）
✓ Worktree 2（程式碼品質）：../work-hooks-review-2（分支：worker-2）
✓ Worktree 3（規格合規）：  ../work-hooks-review-3（分支：worker-3）
```

每個是**實體隔離的資料夾**，三個 AI 同時工作互不干擾。

# 第五部分：雙重安全網（翻車能回滾）

「常在河邊走，哪有不濕鞋」。如果那個二廚搞砸了，比如重構依賴套件時把 `package.json` 整個清空，我們有救命網嗎？

## 安全網一：Checkpoint（時光機）

Claude 內建檢查點機制。在終端機連按兩次 **Esc**（或 `/rewind`）就能開啟時光機，把程式碼與對話歷史退回上一步。系統在你每次送出提示詞後自動建立檢查點，比一直手動 `git commit` 還順暢。

## ⚠️ 但有一個攸關專案生死的盲點

範例 `docs/checkpointing-guide.md` 用紅字警告：

> **Checkpoint 只能追蹤 Claude 透過內部檔案編輯工具（Write/Edit）修改的純文字檔。**
> 它**完全無法追蹤任何透過 bash 終端機指令造成的改變**。

也就是說，如果 AI 不是直接改檔案，而是下了一個指令（`npm install` 更新模組、`mv` 移動資料夾、`rm` 刪檔），這個時光機**救不回來**——一旦破壞發生就是不可逆的。

## 安全網二：Git stash（補上盲點）

所以當你預期 AI 接下來要執行危險的 bash 操作，請回到終端機手動做一層 Git 保護：

```bash
git add -A && git stash
```

| 機制 | 保護範圍 |
|------|---------|
| Checkpoint（Esc+Esc）| 對話 + 文字編輯（Write/Edit）|
| Git stash | bash 危險操作（rm/mv/npm install）|

**兩者互補、不可互換**，結合起來才是真正的安全網。這絕對是無數個被搞爛的專案換來的血淚經驗。

# 第六部分：自我進化（讓 AI 自己開檢討會）

最酷的部分來了。最好的系統是能**自我學習**的系統。怎麼做到？

## 機制：PostToolUse hook + 日誌分析

範例 `hooks/observe-pattern.sh` 是一個 PostToolUse hook——每次 AI 用任何工具（讀檔、跑指令），它都默默把動作結果寫進一個 `patterns.jsonl` 日誌。接著範例 `skills/analyze-patterns/SKILL.md` 讓 AI 定期分析自己的日誌。

## 分析能發現什麼？

字稿的真實案例：AI 分析日誌時發現，過去一週某個 bash 指令連續出現 **5 次 Exit Code 2（權限被拒）**。這時它不會再傻傻撞牆，而是**主動跳出來建議**：

> 「我發現我常常在這裡因為權限問題卡住，我們是不是該修改一下 CLAUDE.md 的規則？」

就像這支 AI 團隊有了潛意識，每週五下午自己開檢討會議，主動提出改進團隊規範的提案。

## 老師的實跑驗證

我完整跑了這個迴圈。先用 `observe-pattern.sh` 記錄 8 筆模擬操作（開發者反覆「git status → npm test」），再用 analyze-patterns 的邏輯分析：

```
| Pattern                          | 次數 | Confidence | 判定 |
|----------------------------------|------|------------|------|
| git status（單一）               | 3    | 38%        | ❌否  |
| npm test（單一）                 | 3    | 38%        | ❌否  |
| 序列「git status → npm test」    | 3    | 75%        | ✅候選 |
```

**關鍵洞察**：單一指令信心不足（38%），但**序列**達標（75%）——AI 偵測到「這兩個指令總是成對出現」，主動建議把它打包成一個 `/git-test` skill。這就是系統自我進化的真實樣貌。

# 第七部分：團隊生態（從個人到社群）

當你把這套自我修正的流程打磨成熟後，可以把所有規則、自訂指令、子代理**打包成一個帶名稱空間的外掛（plugin）**：

- `plugin-example/.claude-plugin/plugin.json`：外掛的身分證（名稱、版本、作者）
- `plugin-example/hooks/hooks.json`：外掛內建的 hook（例如 Write/Edit 後自動跑 lint）
- `scripts/install-skill.sh`：同事只要一行 `install-skill` 就能裝上你精心調教的配置

你甚至可以去官方社群（如 AgentSkills.io）下載世界上其他頂尖開發者寫好的技能。這讓 AI 的應用**從你個人的桌面工具，昇華成整個開發社群的生態系統**。

# 結語：從 AI 使用者，到 AI 工程團隊管理者

我們今天走過一條完整的生產化道路：

| 機制 | 解決的問題 |
|------|-----------|
| 七階段 SOP | AI 衝動、過早寫程式 |
| orchestrate 動態編排 | 流程太官僚、殺雞用牛刀 |
| confidence-check + 四靈魂拷問 | AI 幻覺、瞎掰 |
| 三窗格 worktree 分工 | 大型重構迷失方向 |
| Checkpoint + Git stash 雙網 | 翻車無法回滾 |
| observe-pattern + analyze-patterns | 系統不會自我改善 |
| plugin 打包 | 知識只在你腦袋裡（部落知識）|

這已經超越「如何寫提示詞」，根本是一堂扎扎實實的 **AI 工程團隊管理學**。

## 留給你的思想實驗 🤔

今天我們看到 AI 已經能：分析自己的失敗行為、主動建議修改自己的規則、甚至自己編排開發的七個階段。

如果這一切都自動化了——

> 身為開發者的你，未來的核心價值究竟在哪裡？
> 你到底還是不是那個敲鍵盤寫程式的人？
> 還是你會慢慢變成那個坐在窗格外面、冷眼看著 AI 團隊互相討論除錯，
> 而你唯一的動作，只是偶爾在安全檢查點跳出來時**按一下 Enter** 的人？

把寫程式變成純粹的**決策與監管**——這是你未來每次部署 AI 系統時，都值得好好思考的問題。

下次你在終端機前，面對 AI 給出的一大段漂亮程式碼時，**別急著存檔**，先試試那四個靈魂拷問，看它到底是真的懂，還是只是在對你自信地閃爍其詞。
