# 第七章範例程式碼使用指南 — 寫給完全新手的你

> 這份文件的目標：你是一位剛入職的新人工程師，從來沒用過這些工具。
> 看完這份文件，你會知道 `part7-workflows/` 資料夾裡的 8 樣東西
> **是什麼、什麼時候用、按什麼順序用**。

---

## 開場故事：為什麼需要這些工具？

想像你請了一位非常聰明、但非常急性子的助手（就是 AI）。

你跟他說：「幫我修一下購物車的結帳按鈕。」

三秒鐘後，他改了 400 行程式碼，還順便「幫你最佳化了系統架構」——
結果你的資料庫連線設定全部被清空了。

**AI 不是笨，是太急著表現。** 它最常見的失敗模式叫做「過早開始寫程式」：
需求還沒搞清楚，就開始狂改你的檔案。

第七章的範例程式碼，就是一整套「管住這位急性子助手」的工具箱。
總共 8 樣工具，分成 4 層，每一層解決一個問題。

---

## 全局地圖：4 層工具箱

把整個 `part7-workflows/` 想像成一間餐廳的管理制度：

| 層 | 工具 | 餐廳比喻 | 解決的問題 |
|---|------|---------|-----------|
| 第 1 層 | dev-workflow、confidence-check、orchestrate | 廚房的標準作業流程（SOP） | AI 太急著動手 |
| 第 2 層 | hallucination-detection.md | 食材驗貨手冊 | AI 瞎掰不存在的東西 |
| 第 3 層 | cascade、checkpointing-guide | 三位廚師分工 + 廚房滅火器 | 大型任務失控、出事救不回來 |
| 第 4 層 | observe-pattern、analyze-patterns、plugin、install-skill | 每週檢討會 + 食譜分享 | 經驗無法累積與傳承 |

**新手只要先學第 1 層就夠了。** 第 2、3、4 層等你熟了再說。

## 第 1 層：日常主流程（每天都會用到）

### 工具 ①：dev-workflow — 七階段標準作業流程

**檔案位置**：`skills/dev-workflow/SKILL.md`

**它是什麼**：一份「強迫 AI 照表操課」的流程表。
把它複製到專案的 `.claude/skills/` 資料夾後，
你在 Claude Code 裡輸入：

```
/dev-workflow 翻新金流模組
```

AI 就必須按照以下七個階段走，**一步都不能跳**：

```
階段 1：腦力激盪    → 禁止寫任何程式碼！只能用文字想清楚要做什麼
階段 2：Worktree    → 開一個隔離的工作資料夾（避免弄壞你的主程式）
階段 3：規劃        → 跑 confidence-check 自我檢查（見工具 ②）
階段 4：Sub-agent   → 派小助手去調查舊程式碼長什麼樣
階段 5：TDD         → 先寫測試，再寫程式（先證明你懂問題）
階段 6：審查        → 檢查安全性和品質
階段 7：完成        → 存檔、清理、收工
```

**白話比喻**：就像新人廚師進廚房，主廚規定：
先看食譜（階段 1）→ 用備用爐台練習（階段 2）→ 列出要用的食材（階段 3）
→ 問前輩這道菜的眉角（階段 4）→ 先試吃標準（階段 5）→ 主廚驗收（階段 6）→ 上菜（階段 7）。

**搭配圖**：資料夾裡的 `seven-stage-workflow.png` 就是這七個階段的流程圖，
建議搭配著看。

### 工具 ②：confidence-check — 開工前的 5 項自我檢查

**檔案位置**：`confidence-check/SKILL.md`（和 `skills/confidence-check/SKILL.md` 內容相同）

**它是什麼**：一張「動手前的檢查清單」。AI 必須對 5 個問題自我評分，
**5 題至少答對 4 題（90%）才准開始寫程式**。

| 編號 | 檢查項目 | 在防什麼災難 |
|------|---------|------------|
| C1 | 重複實作檢查 | 公司早就有一份「信用卡驗證模組」，AI 不知道，又重寫了一份 → 兩套邏輯互相打架 |
| C2 | 架構合規檢查 | AI 寫的程式違反了團隊的分層規定 |
| C3 | 官方文件檢查 | AI 用的 API 在現在這個版本根本不存在 |
| C4 | 開源參考檢查 | 別人早就做過了，不用重新發明輪子 |
| C5 | 根本原因確認 | 還沒搞清楚 Bug 為什麼發生，就開始瞎改 |

**白話比喻**：出門前的口訣「鑰匙、錢包、手機」。
少帶一樣可能沒事，少帶兩樣今天一定出事。

**怎麼用**：它通常不是單獨用，而是被七階段流程的「階段 3」自動呼叫。
但你也可以隨時手動輸入 `/confidence-check 我要加一個匯出功能` 單獨檢查。

---

### 工具 ③：orchestrate — 智慧入口（避免殺雞用牛刀）

**檔案位置**：`orchestrate/SKILL.md`

**它解決的問題**：你可能會想——「我只是要改個按鈕顏色，
也要跑七階段、開隔離資料夾？太麻煩了吧！」

沒錯。如果每件小事都走完整流程，大家很快就會放棄這套系統。
所以需要一個「智慧分流員」。

**它是什麼**：你輸入任務類型，它自動幫你選「適合這個任務大小」的流程：

```
/orchestrate bugfix 購物車按鈕壞掉
```

| 你輸入的類型 | 它選擇的流程 | 為什麼 |
|------------|------------|-------|
| `feature`（新功能） | 定需求 → 檢查 → 設計文件 → TDD → 更新文件 | 新東西要想清楚再做 |
| `bugfix`（修 Bug） | 重現錯誤 → 找根本原因 → 最小修復 → 加迴歸測試 | 跳過腦力激盪，因為問題已經很明確 |
| `refactor`（重構） | 先確認測試覆蓋 → 漸進式遷移 → 每步驗證 | 不能一次大改，要小步前進 |
| `security`（資安） | 唯讀調查 → 比對弱點 → 隔離修復 → 資安審查 | 最危險，所以最嚴格 |

**bugfix 有一條鐵律**：AI 在寫任何修復程式碼之前，
必須先寫出一個「能重現這個 Bug 的失敗測試」。
寫不出來？系統直接鎖死，不准碰程式碼。
因為——寫不出失敗測試，代表你根本不知道問題在哪，後面全是瞎猜。

**白話比喻**：醫院的檢傷分類。感冒不用進開刀房，
但心臟病發不能只給你普拿疼。

---

### 第 1 層總結：日常使用順序

```
接到任務
   ↓
輸入 /orchestrate <類型> <任務名>     ← 一律從這裡進入
   ↓
小任務 → 走簡化流程，很快做完
大任務 → 轉入 /dev-workflow 七階段
   ↓
不管哪條路，動手寫程式前
都會經過 /confidence-check 檢查（5 題對 4 題才放行）
```

## 第 2 層：防幻覺手冊（AI 瞎掰時用）

### 工具 ④：hallucination-detection.md — 四個靈魂拷問

**檔案位置**：`hallucination-detection.md`

**注意**：這不是程式，是一份**給你（人類）看的手冊**。

**它解決的問題**：AI 有時會非常自信地告訴你
「我查過官方文件了，Stripe 有一個 Refund All 的 API」——
但那個 API 根本不存在，是它「通靈」出來的。
這就叫「幻覺」。

**怎麼用**：當你覺得 AI 講的話怪怪的，**不要跟它爭論**，
直接把這四個問題砸過去：

```
Q1：「給我官方文件的確切網址和章節。」
Q2：「這個功能是哪個版本才引入的？你查過嗎？」
Q3：「有沒有替代做法？各自的優缺點是什麼？」
Q4：「舉三個會讓這個做法失敗的情境。」
```

**為什麼有效**：捏造一段「聽起來很順」的程式碼很容易，
但捏造一個「點得開的網址」幾乎不可能。
這逼 AI 必須拿出實體證據，而不是靠模糊記憶瞎猜。

**加碼：七個紅旗訊號**。手冊還教你「聽懂 AI 的心虛」，例如：


- 「應該是…」「大概…」「似乎…」→ 把猜測當事實講
- 「快 30%」→ 沒有出處的效能數字
- 「我相信這是正確的」+ 一大堆複雜術語 → 典型的自信滿滿式心虛

## 第 3 層：大型任務與安全網（做大事之前看）

### 工具 ⑤：cascade-start.sh — 三位廚師同時開工

**檔案位置**：`cascade/cascade-start.sh`

**它解決的問題**：超大型任務（例如整個系統換框架）只靠一個 AI，
做到一半一定「斷片」——改了東邊忘了西邊。

**它是什麼**：一個腳本，執行後自動建立 3 個隔離的工作資料夾（git worktree），
讓你同時開 3 個 Claude，各司其職：

```bash
bash cascade/cascade-start.sh 大重構
```

| 視窗 | 角色 | 用的模型 | 權限 |
|------|------|---------|------|
| Worker 1 | 主廚（架構師） | 最聰明但最貴的 | 只能看、只能指揮，不能寫程式 |
| Worker 2 | 二廚（實作者） | 速度與能力均衡的 | 完整讀寫，負責真正寫程式 |
| Worker 3 | 品管（驗證員） | 最快最便宜的 | 只能讀檔案和跑測試 |

**白話比喻**：主廚雙手抱胸出一張嘴，二廚在爐火前瘋狂炒菜，
品管在出菜口試吃。三個人**永遠不會互相弄髒對方的工作檯**。

---

### 工具 ⑥：checkpointing-guide.md — 時光機的使用說明（含致命陷阱）

**檔案位置**：`docs/checkpointing-guide.md`

**它是什麼**：Claude Code 內建「檢查點」功能——
每次你送出指令，系統自動存一個還原點。
出事了？連按兩次 `Esc`，程式碼和對話全部退回上一步。比 git 還方便。

**但是！這份指南最重要的就是這個紅字警告**：

> ⚠️ 檢查點**只能**還原「AI 用檔案編輯工具改的文字檔」。
> 如果 AI 是用**終端機指令**搞破壞——例如 `npm install` 更新了套件、
> 用指令搬移了資料夾——**時光機完全救不回來，破壞不可逆**。

**所以正確做法是雙重保險**：

```
預期 AI 要做危險操作前，你手動輸入：
git add -A && git stash     ← git 保護「指令造成的改變」
（AI 檢查點則保護「文字編輯」）
兩個一起用，才是真正的安全網。
```

## 第 4 層：自我進化與分享（系統成熟後玩的）

### 工具 ⑦：observe-pattern.sh + analyze-patterns — AI 的每週檢討會

**檔案位置**：`hooks/observe-pattern.sh` 和 `skills/analyze-patterns/SKILL.md`

這兩個是一對搭檔，像「行車記錄器 + 看回放」：

**observe-pattern.sh（行車記錄器）**：
掛在系統的 PostToolUse 掛鉤上，AI 每做一個動作
（讀檔、跑指令…），就默默記一筆到日誌檔 `patterns.jsonl`。

**analyze-patterns（看回放）**：
你定期輸入 `/analyze-patterns`，它分析日誌找出規律：

```
偵測重複出現 3 次以上的操作
→ 信心分數 ≥ 70%：建議做成新的 Skill（自動化起來！）
→ 信心 40-70%：再觀察看看
→ 信心 < 40%：不理它
```

**實際案例**：AI 發現自己一週內同一個指令被權限拒絕了 5 次，
它會主動建議：「我們是不是該修改一下設定？」
——就像團隊每週五開檢討會，把「只有老鳥才知道的眉角」變成白紙黑字的制度。

---

### 工具 ⑧：plugin-example + install-skill.sh — 食譜的打包與分享

**檔案位置**：`plugin-example/` 和 `scripts/install-skill.sh`

**plugin-example（打包出去）**：
你調教好的整套工具（Skills + Hooks），可以打包成一個「外掛」。
同事只要一行指令安裝，就立刻擁有你的「米其林廚房配置」。

**install-skill.sh（安裝進來）**：
反過來，別人在 GitHub 上分享的好用 Skill，用這個腳本一鍵裝進你的專案：

```bash
./install-skill.sh code-review https://github.com/example/skills
```

**意義**：你的經驗從「個人桌面工具」升級成「整個團隊、甚至整個社群的生態系」。

## 最後：新手上路的建議順序

不要一次全學。照這個順序，一週上手一樣：

```
第 1 週：只裝 confidence-check
         每次動手前跑一次 5 項檢查 → 立刻有感，馬上少踩坑

第 2 週：裝 orchestrate
         養成習慣：所有任務都從 /orchestrate 進入

第 3 週：遇到大任務時用 dev-workflow 七階段
         並把 hallucination-detection 的四個拷問貼在螢幕旁邊

第 4 週：讀 checkpointing-guide，學會 git stash 雙重保險
         大型重構時試試 cascade 三廚師模式

之後：   掛上 observe-pattern 日誌，每週跑 /analyze-patterns
         成熟後打包成 plugin 分享給團隊
```

## 一個常見疑問

**Q：為什麼 confidence-check 和 orchestrate 在資料夾裡各有兩份？**

A：`skills/` 底下那份是「安裝後該有的樣子」（直接複製到你專案的
`.claude/skills/` 就能用）；根目錄那份只是書中展示用的副本。
兩份內容一模一樣，不用糾結。
