  4. 如果我現在照你說的步驟做，最可能遇到什麼錯誤？

動態編排 /orchestrate
依任務類型選擇對應的工作流路徑。
🐛 Bug Fix 流程
L1 幻覺偵測 → L2 信心檢查 → S4 Sub-agent 探索根因 → S5 TDD 修復 → S6 審查 → S7 Commit

⚡ 特點：跳過 S1 腦力激盪，因為問題已知；L1 優先排除「AI 幻覺診斷」的干擾

✨ New Feature 流程
S1 腦力激盪 → L2 信心檢查 → L3 動態編排 → S2 Worktree → S4 探索 → S5 TDD → S6+S7

⚡ 特點：完整 7 階段，S2 Worktree 隔離避免污染主線

🔧 Refactor 流程
L6 分析歷史模式 → L2 信心檢查（C2+C5） → S2 Worktree → L5 Multi-agent → S6 審查

⚡ 特點：L6 先看歷史日誌了解現有模式；L5 多 worktree 並行審查不同面向

🔒 Security 流程
L1 幻覺偵測（優先） → L2 全項通過（5/5） → S2 獨立 Worktree → L7 Plugin 封裝結果

⚡ 特點：L2 門檻升至 5/5（全通過）；安全修補不允許任何不確定性

七階段工作流 + Checkpoint
點擊圓點或按鈕逐步走完 S1–S7。每個階段都有前置條件。
Checkpoint vs Git Stash 對照
保護工具保護範圍盲點何時用

5
多 Agent Worktree — 三角色分工
一鍵展開三個獨立戰場，主線 main 完全不受影響。
main 分支
→ cascade-start.sh demo-task
Worker 1 — 架構師
Opus — 最強推理

Plan Mode 鎖定，禁止 Write/Edit
負責：S1 腦力激盪 + S3 規劃
Branch: demo-task-worker-1-{ts}

Worker 2 — 實作者
Sonnet — 成本/能力平衡

完整讀寫權限
負責：S4 探索 + S5 TDD
Branch: demo-task-worker-2-{ts}

Worker 3 — 驗證者
Haiku — 快且便宜

唯讀 + 執行測試
負責：S6 審查
Branch: demo-task-worker-3-{ts}

為什麼用 Worktree 而非新 Branch？ Branch 只是 git 指標切換，仍共享同一實體工作目錄；三個 Claude 實例會互相蓋掉彼此的檔案。Worktree 是獨立實體資料夾，互不干擾。
# 建立三個 worktree
bash cascade-start.sh demo-task
# 清理
git worktree remove ../work-demo-task-{1,2,3}
git worktree prune

觀察 Hook + 自我進化
PostToolUse Hook 把每次工具操作寫入 JSONL，再用 /analyze-patterns 分析信心分數。
日誌模擬 — patterns.jsonl
信心分數：55% （出現次數 / 總操作數 × 100）
信心分數行動理由
≥ 70%Skill 候選真正的工作習慣，值得制度化
40–69%持續觀察模式尚不穩定
< 40%不列入候選偶發操作或雜訊
