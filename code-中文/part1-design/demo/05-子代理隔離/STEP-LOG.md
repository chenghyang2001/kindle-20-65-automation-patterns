## Step 2：理解「迷失在中間效應」

### 概念說明

如果直接在主對話讀取 50 個檔案：

```
主對話 context（有限空間）
  ├── 你的問題
  ├── 檔案 1 的完整內容（2,000 token）
  ├── 檔案 2 的完整內容（1,500 token）
  ├── ...
  ├── 檔案 50 的完整內容（3,000 token）
  └── AI 已經被 50 個檔案的雜訊淹沒
      → 只記得開頭（檔案 1）和結尾（檔案 50）
      → 中間 48 個檔案的細節 → 遺忘 / 幻覺
```

使用 context.fork：

```
主對話 context（保持清晰）
  └── 你的問題 + 等待報告

子代理 context（獨立空間）
  ├── 任務指示
  ├── 50 個檔案（消耗子代理的 context）
  └── 完成後 → 只回傳一頁重點報告給主對話
```

### 思考練習

1. 子代理分析完 50 個檔案後，回傳給主對話的是什麼？
   （全部 50 個檔案的原始內容？還是整理過的報告？）

## 本課重點

```
子代理隔離的三元素：

  context: fork
    → 分岔出獨立的 context 空間
    → 主對話完全不被子代理的讀取操作污染

  agent: Explore
    → 子代理天生傾向「只讀不寫」
    → 適合大量搜尋和分析任務

  allowed-tools: Read, Grep, Glob
    → 只給唯讀工具（沒有 Write / Edit / Bash）
    → 即使 Skill 裡的指示有誤，也不可能造成意外修改

「老闆和研究助理」模型：
  老闆（主 context）：出題 → 等報告 → 做決策
  研究助理（子代理）：深入挖掘 → 整理摘要 → 只回傳精華

兩個指標：
  用子代理：需要讀 10+ 個檔案 / 任務是純分析 / 想保護主 context 清晰
  不用子代理：只讀 1-2 個檔案 / 任務涉及決策和後續行動
```
